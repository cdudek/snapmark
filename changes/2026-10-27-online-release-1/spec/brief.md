# Brief: Snapmark online, release 1 (local)

**Scope: release-scoped.** One exception: "New glossary terms" is lasting and moves to `snapmark-web/docs/ux/glossary.md` in milestone 1.

Release 1 runs on the owner's machine. It ships the public landing page with a waitlist, email-link sign-in (the link is printed to the terminal), organisations, workspaces, invitations, the Chrome extension, feedback with versions, reviews and decision requests, the MCP door for coding agents, the Mac app's localhost bridge and two-way session sync, and the operator area. Google and GitHub sign-in, the GitHub integration, Slack, billing, Resend and the Web Store come in release 2. This spec designs only what release 1 ships. The structure leaves a named place for each release-2 piece, and none of them is drawn as working.

Asks are the `## Asks` table in `intent.md` (A1 to A29), plus A30, which the owner gave during this stage. Job stories J1 to J9 are copied from `intent.md`. J10 and J11 are added here because two groups of screens (settings, devices) serve no J1 to J9 job directly.

**How A30 is read.** It applies to words that sell or welcome: the landing page (headline, subhead, sections, call to action, waitlist confirmation), the invitation and sign-in emails, first-run headlines and empty-state headlines. These speak about what the team gets: decisions that stick, agents that build the right thing, shipping without screenshot ping-pong. They never list features ("Chrome extension, MCP server, versions"). A30 does not touch control labels, menu items, status words or settings. Those stay plain glossary words (Approve, Request Changes, Open), as the design system's voice rule says ("Inside the product: plain words that name the object and the outcome"). A feature may appear lower on the landing page only to answer "how?".

## Visible Success

The owner, running everything locally, opens a staging page in Chrome, clicks the Snapmark icon, picks the Checkout summary card, draws a box, writes "Total should be bold", and sends. Within seconds the web app's Open list shows the item with "Checkout summary" and `src/cart/CartTotal.tsx:42`. Dana posts a mockup as v1 and requests a decision; Priya votes from her phone. Dana approves v1, which marks it decided. Ben's copilot claims it ("In Progress · Ben via Claude"), implements it, and reports v2 with the commit and an after-screenshot. Priya opens Compare, sees v0 and v2 side by side, and approves. The item lands in Done, and the trail reads top to bottom without a word of explanation. Every screen has one blue button and plain words.

## UI-risky screens (the prototype draws these)

New patterns, dense layouts, or never drawn before for this product:

1. **App shell with the sidebar and the ⌘K command menu**: the first web surface; sets density and calm for everything else.
2. **Inbox (desktop)**: a new mixed list of decision requests, review requests, questions, mentions and answers.
3. **Feedback view**: screenshot centre with references and marks, version tabs, Compare (side by side), the right panel with Thread and Details, the review footer, copilot and guest entries. The densest screen.
4. **Decision request**: the Request a Decision dialog and the decision card with the tally, open and closed.
5. **Phone inbox and phone feedback view**: screenshot on top, thread, reply field, fixed Approve / Request Changes / Vote bar.
6. **Extension capture and compose**: the popup (signed out, signed in, guest, Mac app not running), the picker overlay with the chip, the drawing toolbar, the compose panel with code location found and not found, the sent confirmation.
7. **Device consent**: read-only by default with write scopes to opt into (A28).
8. **Operator waitlist**: table with selection and bulk invite.
9. **Landing page with waitlist**: A30 copy at hopes-and-dreams level; first public face.

Standard settings forms, the account pages, the legal pages and the Mac app's Online tab follow existing patterns and are not risky.

- **Letter case on the web:** Title Case for buttons, menu items, tabs, sidebar items, chips, table headers, titles and headings; sentence case for field labels, switch labels, placeholders, messages and full-sentence headlines. The owner can still change it (`owner-decisions.md` #19).
- **The image word:** "Screenshot" on screen; "Capture" only as the verb and the button (WRD-4). `capture` stays the API and table name.
- **Numbered circles:** "Reference"; "mark" for anything drawn; "mark colour" for the picked colour.
- **Guests:** A31 decides it: guests comment, draw and vote; Approve and Request Changes are off with a reason, on desktop and phone alike.
- **Extension capture shortcut:** ⌘⇧K on a Mac, Ctrl+Shift+K elsewhere, changeable at `chrome://extensions/shortcuts`; never ⌘1–⌘9 (owner, 2026-09-28). The conformance check found no Chrome clash for it.

Still open, in `owner-decisions.md`: whether a Comment-kind feedback goes through the status flow (#26; the spec follows "yes, the same rule").
