# Plan: finish Snapmark, everything but selling

> Four milestones in one go: editor polish, capture bar and Settings, tall captures as tiles, then Electron 45. Each one is checked, validated and released before the next one's PR opens; the build never waits.

A person with no context builds from this file alone. [intent](intent.md), [facts](facts.md) and [questions](questions.md) are for the gate. Specs: [spec/editor.md](spec/editor.md) (milestone 1), [spec/capture-and-settings.md](spec/capture-and-settings.md) (milestone 2), [spec/ia.md](spec/ia.md), [spec/interaction.md](spec/interaction.md), [spec/screens.md](spec/screens.md), [spec/microcopy.md](spec/microcopy.md) (milestone 3).

## How this is delivered (one go)

- One `/goal` (below) builds all four milestones. The owner pastes it once.
- Features are commits. **No check, lint or test runs per feature or per commit.** The "proof" of each step below is checked once, at its milestone.
- Each milestone, once: `verify_gate.py milestone` (format, lint, typecheck, unit tests, `smoke:background`), the UX and code reviews, and **validation** of every fact and ask in [validation.md](validation.md). One fix round, one PR to `main`, auto-merge, one release, installed on the owner's Mac.
- Milestone `n+1` is cut from `n` and builds while `n`'s PR waits. Its PR opens after `n` merges (`git rebase --onto origin/main milestone/finish-app-<n>`).
- Questions never block: [questions.md](questions.md) holds each with the default taken. An answer becomes an ask of the next milestone.

## Approach

- **What changes:** the editor's toolbar, header and Highlighter; two new windows (capture bar, Settings) and a rebuilt Keyboard Shortcuts window. Also tall screenshots saved as parts, and Electron 45.
- **What stays the same:** saved sessions, every existing shortcut except ⌃⇧5, and how a screenshot that fits is saved. ⌃⇧5 now opens the bar instead of a popup menu with the same choices.
- **Why this way:** the approved mocks in `design-explorations/` are the target for milestones 1 and 2. Tiles keep its approved spec; upgrades go last so they test everything built before them.
- **Rejected:** one PR per feature — the owner's call on 2026-10-25: checks and validation per milestone only.
- **Rejected:** one button per tool in the toolbar — reverses the accepted toolbar ADRs; asked in [questions.md](questions.md) with groups kept as the default.
- **Rejected:** folding Keyboard Shortcuts into Settings — the guidelines want it one key away (⌘/), and the mock is a wide two-column window.

Tiles, as approved in its own spec:

- **What changes:** on save, a tall screenshot becomes one image at the part width plus overlapping parts, and its entry links the parts.
- **What stays the same:** every screenshot that is not tall, byte for byte; numbering, the count, the session window, and every key and menu item.
- **Why this way:** each part is within Claude's limits, so the agent reads the page at about its captured width. The owner still handles one screenshot.
- **Rejected:** 1568 px wide parts — slightly sharper, for about 60 % more parts and tokens (17 instead of 11 at 2560 × 16 000).
- **Rejected:** shrinking the whole image, as today — an 8000 px page arrives about 250 px wide.
- **Rejected:** a grid of tiles — a page scrolls one way, and columns cut lines of text in half.
- **Rejected:** parts only, without the one image — the session window, the PDF, Save As… and Discarded need the whole page.
- **Rejected:** cutting every image taller than 1568 px — normal tall windows read fine whole; the two-thirds rule leaves them alone.
- **Rejected:** parts in the PDF — a person would see every overlap strip twice.
- **Rejected:** a setting for part width — nobody asked for it.

The decision is recorded in [docs/designs/2026-10-25-adr-tall-screenshots-saved-as-parts.md](../../docs/designs/2026-10-25-adr-tall-screenshots-saved-as-parts.md).
