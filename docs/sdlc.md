# The SDLC: how work moves through this repo

This repo follows the AI-native SDLC on the milestone process: the agent drafts, the engineer
confirms twice, and everything after runs inside `/goal`. `omr-dev:sdlc-run` drives it from
`sdlc.json`. GENERATED by `sdlc-run adopt` — edit `sdlc.json` and re-run, or edit the
Repo-specific section below.

```
changes/<date>-<KEY>-<slug>/
  decisions.json        ticket · design · size · kind · milestone
  intent.md             ## Asks, job stories, success measure
  spec/                 the UX plan: brief · ia · interaction · screens · conformance · validation
  facts.md              EARS facts citing asks, screens and test tags
  plan.md               where things go · feature PRs · Done · Goal handover
  done.json, lock.json  the criteria as data, and their hash at approval
  milestone.md          features and states · outcome
docs/designs/
  INDEX.md              one line per design and decision, generated: read this first
  <date>-<type>-<slug>.md   a design, or one decision (type adr) with status and supersedes
```

A decision is a file of its own, never a row appended to a log. A design says what is true
now and is edited in place. After adding or changing either, run
`python3 scripts/design_index.py write`; the guardrail test fails on a stale index.

## Install once per machine

## Stages

| Stage       | What happens                                                                                                                                         | Touchpoint                                            |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 1 Intent    | One dialog (ticket, design file, size, kind, milestone); asks verbatim; the agent drafts `intent.md`.                                                | engineer confirms intent                              |
| 2 UX plan   | `omr-ux` design, sitemap, conformance, words; one validation pass. Skipped for size `none` or `ux: off`.                                             | none                                                  |
| 3 Facts     | Facts cite asks, screens and the E2E tag that proves them; plain-language lint.                                                                      | none                                                  |
| 4 Tech plan | Where things go, feature PRs, Done, the goal per feature.                                                                                            | one gate for all three, then `verify_gate.py approve` |
| 5 Build     | Per feature inside `/goal`: tests, build, `verify_gate.py feature`, a PR into `milestone/<slug>`, a UX review of the screens it changes, auto-merge. | none                                                  |
| 6 Milestone | Heavy checks on the milestone diff, one findings list, one fix round, `verify_gate.py milestone`, one PR to the milestone's parent.                  | engineer accepts                                      |
| 6p Project  | Only for work spanning several milestones: rebase `project/<slug>`, re-check the whole project diff, one PR to the default branch.                   | engineer accepts                                      |
| 7 Outcome   | Archive on merge; read the success measure after release.                                                                                            | engineer reads it                                     |

### Branches

```
<default> ─── milestone/<slug> ─── <feature branches>            one milestone
<default> ─── project/<slug> ─── milestone/<slug> ─── <features>  a project
```

A project branch exists only for work that spans several milestones. One milestone needs
none.

## Where a change stands

`scripts/sdlc_status.py` turns one verb into a status line. The skill writes
`changes/<id>/status.json` at every step; the status line reads it.

    status line    Stage 5/7 Build · Building F3 · writing e2e F3.1+F3.2 (2 agents) · 2/5 done

Add `python3 scripts/sdlc_status.py line` to your own status-line script; it reads the same stdin
JSON and prints nothing outside an adopted repo. `python3 scripts/sdlc_status.py map` shows every
milestone and the features of the current one.

## Build and test

After the one gate, `python3 scripts/verify_gate.py approve <id>` locks the criteria. Every
feature then runs inside `/goal` with the condition from `plan.md` `## Goal handover`, and ends
on one line from `python3 scripts/verify_gate.py feature <id>`: `VERIFY PASS`, `VERIFY FAIL`
(fix and rerun) or `VERIFY BLOCKED reason=<code>` (stop and ask the engineer).

For a bug, commit the failing test first and set `testLocked: true`. While locked, test files
matching `testGlobs` cannot be edited unless `testEdit` records the user's OK.

Before a PR, `verify` runs once:

    npm run format && npm run lint && npm run typecheck && npm test

## Ask resources

Every image, screenshot, feedback-tool session, recording or file that came with an ask is
copied into `changes/<id>/asks/<source-date>/` and linked from the `Resources`
column in `intent.md`. Links in the change folder stay inside the repo. `sdlc.json`
`feedback` contains repo paths or globs only.
Run `marks.py init <id>` for Snapmark/reference images; fill `marks.json` against fresh headless shots in `verify/shots/`; milestone `owner-marks` checks it.

## Merging: auto-merge on green

One owner, so no tiers (`sdlc.json` `tiers: false`). Every PR merges itself once it is green.

- **Arm it:** `gh pr merge <n> --squash --auto`.
- **What it waits for:** required checks on `main`.

### One go (owner, 2026-10-25)

`sdlc.json` `delivery: "one-go"` overrides the per-feature flow above. Until the kit's next adopt carries the same text, this section is the rule.

- Everything asked for at once is one change. The owner confirms the intent, then the plan, then pastes **one** `/goal` (`plan.md` `## Goal handover`) that builds every milestone in order.
- Features are commits on `milestone/<slug>-<n>`. **No check, lint or test runs per feature or per commit.**
- Per milestone, once: `verify_gate.py milestone` (format, lint, typecheck, unit tests, `smoke:background`), the UX and code reviews, and **validation**: every fact and ask of the milestone exercised in the built app, one row each in `validation.md` (expected, observed, evidence, verdict). A `not met` row blocks. One fix round, one PR to `main`, auto-merge, one release.
- Milestone `n+1` is cut from `n` and builds while `n`'s PR waits; its PR opens after `n` merges (`git rebase --onto origin/main milestone/<slug>-<n>`).
- **Questions never block.** They go to `questions.md` with the default taken, and the owner is told in one line. An answer becomes an ask of the next milestone.
- The goal stops only on `VERIFY BLOCKED` or a Critical or High that would be deferred.
