# The SDLC: how work moves through this repo

This repo follows Anthropic's AI-native SDLC playbook
(<https://academy.claude.com/courses/ai-native-sdlc-playbook>): each stage ends by
committing an artifact, the commit starts the next stage, and humans sit at the approval
gates rather than on every line. The kit skill `omr-dev:run-sdlc` walks it, reading
`sdlc.json` at the repo root; this page is the reference. GENERATED by `run-sdlc adopt`
— edit `sdlc.json` and re-run, or edit the "Repo-specific" section at the end, which
`adopt` keeps.

```
 docs/designs/<date>-<slug>.md            a design that outlives one PR · status · edited in the change's PR
 Linear issue (project for a design)         status record; branch from Linear autolinks the PR
      ▼
 changes/<date>-<KEY>-<slug>/        open change = content record, committed at every gate
   (<date>-<slug> when the change has no Linear issue)
   intent.md   what · why · constraints      (plannotator interview; PM review via a Linear document)
   facts.md    testable outcomes             (plannotator facts UI)          = the playbook's spec.md
   plan.md     files · order · proof · risks · Done   (plannotator annotate --gate)
      ▼
 build   .worktrees/<slug> · /goal on the Done section · hooks (lint on edit, blocked commands, verify on stop)
      ▼
 PR      claude-review.yml + REVIEW.md → merge-gate → auto-merge on green
      ▼
 changes/archive/<year>/<year-month>/<same name>/   moved when the PR is green, never renamed; history
      ▼
 main → CI green → deploy
```

## Install once per machine

    npm run sdlc:tools

That runs the plannotator installer, installs its Claude Code plugin (the `ExitPlanMode`
gate) and the `plannotator-setup-goal` skill, then tells you to restart Claude Code. The
`SessionStart` hook nags until both are present. Manual equivalent:

    curl -fsSL https://plannotator.ai/install.sh | bash
    claude plugin marketplace add backnotprop/plannotator
    claude plugin install plannotator@plannotator
    npx skills add backnotprop/plannotator/apps/skills/extra --global --skill plannotator-setup-goal --agent claude-code --yes

Linear: in Claude Code run `/mcp` and connect "claude.ai Linear". The connector is
flaky — the skill retries twice and then asks you for the issue id.

## Designs and changes

| Thing                                                                                     | Folder                          | Lifetime                                                 | Linear                            |
| ----------------------------------------------------------------------------------------- | ------------------------------- | -------------------------------------------------------- | --------------------------------- |
| the work of ONE PR: `intent.md` · `facts.md` · `plan.md` · `handover.md`                  | `changes/<KEY>-<slug>/`         | archived at merge                                        | **issue** (1:1 with the PR)       |
| a **design** that outlives one PR: data model, ADR, screen-by-screen design, API contract | `docs/designs/<date>-<slug>.md` | as long as the behaviour exists; `status` · `supersedes` | **project** (1:1 with the design) |
| runbooks, architecture, security                                                          | `docs/`                         | forever                                                  | —                                 |

**A recurring mistake gets a guardrail, not a lesson.** If something goes wrong twice, the
fix is a check that makes the third time impossible: a test, a CI gate, a lint rule, a line
in the skill that does the work. Writing it down for people to remember is how it happens a
third time. There is no `lessons` folder — either the rule is enforced somewhere, or it
lives in the document it governs.

Two things, two lifetimes (the split OpenSpec makes; Spec Kit and Kiro keep one living
folder per feature, ADRs/RFDs number and supersede):

|        | `docs/designs/`                                                                                         | `changes/`                                                               |
| ------ | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| is     | a **design** that outlives one PR: data model, ADR, screen-by-screen design, API contract               | one **change** = one PR                                                  |
| lives  | for as long as the behaviour exists; `status` moves, `updated:` bumps, `supersedes` links a replacement | days; archived when the PR is green                                      |
| edited | in the PR of the change that alters the behaviour (`plan.md › Design changes`)                          | at each gate, as commits                                                 |
| Linear | a **project**; the design is attached as a document (permalinks, never paths)                           | an **issue** per change; intent attached as a document when a PM reviews |

**Issue = change = PR, always. Project = design.** A project may hold one issue or ten; a
design file is required only when the project spans more than one PR or the behaviour needs
a standing description. A change without a design is normal (a fix, a small feature). A
design without changes is a design nobody started. The playbook's **spec.md** (the delta of
one change) is `facts.md` inside the change folder; the kit never calls a file "spec". The link is checked both ways by the guardrail test: a change's
`design:` must resolve, and the design's Milestones section must list the change.

Three PR shapes run without a change folder or a Linear issue, on purpose: image-tag
bumps (the deploy bot); moves and renames that add no work item (a file into
`docs/history/`, the archive step when it came after the merge); and a design written or
re-planned before its changes exist — its roadmap rows name the changes that will each get
a folder. They still get the review.

## The artifact chain

| Artifact                                         | Made by                                        | Gate                                                                               | Playbook name                                          |
| ------------------------------------------------ | ---------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `intent.md` (optional when the ticket states it) | the originator with Claude, from the interview | the originator, or a PM via the Linear document (`status: in-review` → `approved`) | intent.md                                              |
| `facts.md`                                       | plannotator facts review                       | accept / edit / remove each fact                                                   | spec.md (the delta)                                    |
| `plan.md`                                        | Claude, from the codebase                      | `plannotator annotate --gate` → approved                                           | plan.md; its **Done** section is the `/goal` condition |
| `handover.md` (optional)                         | a session that stops mid-build                 | none                                                                               | —                                                      |

Rules, enforced by the guardrail test (`tests/sdlc.test.ts`):

- Folder `<created>-<KEY>-<slug>`, and `<created>-<slug>` when the change has no Linear
  issue. Archiving moves it under `archive/` unchanged. `facts.md` and `plan.md` always; `intent.md`
  when written has the five playbook sections.
- Every artifact's frontmatter has `linear:` matching the folder's key (`none` when it has
  none), `created:` matching the date in the folder name while the change is open, `change:` = the
  folder name, `design:` (a path under `docs/designs/` or `null`), `status`, `reviewed_by`,
  `approved_at`; archived ones `archived_at`.
- `plan.md` has `## Order of work` (a task list), `## Done`, `## Revisions`.

**History is git, made legible.** Each gate is one commit (`changes(<id>): intent approved
by <who>`, `facts accepted`, `plan approved`, `plan revised — <why>`, `archived`); the
plannotator JSON (interview, facts review, plan annotations) stays in the folder; a plan
changed after approval gets a dated line under `## Revisions`. `run-sdlc status <id>`
prints the plan's log. No `v1`/`v2` copies — a plan that changes shape is a new change.

**Every artifact is plain English, built to scan.** Short sentences, active voice, one
idea per sentence. Headings and lists instead of prose; a paragraph is at most three
sentences. A bold label starts every bullet that carries a value (`- **Deadline:** …`).
Paths, commands and table names stay exact, in backticks. The kit's templates set the
shape — fill them, do not restyle them. A reviewer who has to read a section twice sends
it back.

**Linear is the status record, the repo is the content record.** The branch name and
`Fixes <ID>` do the syncing. What goes to Linear goes through `linear-safe.py`: repo paths
become permalinks at the current SHA, laptop paths are refused. A design or an intent posted
as a Linear document carries the permalink it was copied from.

## Build: `/goal`

After the plan is approved, run `/goal`. Its text opens with the pointer to the work —
"Build `changes/<id>/plan.md` in its order of work; every outcome in `facts.md` must hold;
tick tasks as they land; log departures under `## Revisions`" — then the **Done** section
of `plan.md` verbatim. Done alone is the test, not the work: it says "every task above is
ticked" and a fresh session has no "above". Claude
keeps working until a separate evaluator judges the condition met, judges it impossible,
or a turn hits an error you must fix. Auto mode removes per-tool prompts; `/goal` removes
per-turn prompts. `/goal` shows status, `/goal clear` stops it.

## Hooks (`.claude/settings.json`, scripts in `.claude/hooks/`)

All five read `sdlc.json`; none carries a repo-specific command.

| Event                            | Script              | Does                                                                                                                                                                                                                                                                                          |
| -------------------------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SessionStart`                   | `session-check.sh`  | tells Claude when plannotator or its plugin is missing                                                                                                                                                                                                                                        |
| `PermissionRequest ExitPlanMode` | `plan-gate.sh`      | opens the plan in plannotator; steps aside when the plugin is installed or the binary is absent                                                                                                                                                                                               |
| `PreToolUse Bash`                | `gate-bash.sh`      | blocks every `blocked[]` pattern in `sdlc.json` — exit 2 with the route                                                                                                                                                                                                                       |
| `PreToolUse Edit\|Write`         | `chain-gate.sh`     | refuses a write the chain has not earned yet: the folder before the step 0.5 dialog answered, `facts.md` before the intent decision, `plan.md` before the facts are approved, source before the plan is approved with a filled `## Goal handover`. Only when this branch has a change folder. |
| `PostToolUse Edit\|Write`        | `lint-on-edit.sh`   | runs the matching `lintOnEdit` command on the one file that changed                                                                                                                                                                                                                           |
| `Stop`                           | `verify-on-stop.sh` | runs `verify` when a `verifyDirty` file is uncommitted; failure blocks the stop                                                                                                                                                                                                               |

`permissions.deny` keeps `.env*`, `**/secrets/**` and `**/.secrets/**` unreadable. Every
block prints why and how to get it approved.

## Merging: auto-merge on green

One owner, so no tiers (`sdlc.json` `tiers: false`). Nobody else is asked and nobody is
shown. Every PR merges itself once it is green.

- **Arm it:** `gh pr merge <n> --squash --auto`, as soon as the PR is open.
- **What it waits for:** the ruleset on `main` requires `merge-gate` (while
  `claude` is on) and CI if the repo has it. Auto-merge waits until they are green.
- **Who arms it:** you, never `GITHUB_TOKEN`. A merge is performed by whoever armed it, and
  a push by `GITHUB_TOKEN` triggers no workflows — `main` would land with no CI
  run and no deploy.

Set `tiers: true` and re-run adopt when a second owner joins.

## Claude in CI

| Workflow            | Trigger                                                                            | Does                                                                                                                                                                                                                                                |
| ------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `claude-review.yml` | a non-bot, non-draft PR when it opens, leaves draft, or gets the `re-review` label | one Sonnet pass against `REVIEW.md` (≈$1, capped at $2), inline comments, tally with the reviewed SHA; `merge-gate` runs on every push and fails on any Important or when the head is not the reviewed SHA — add `re-review` when the head is ready |
| `claude.yml`        | `@claude` in a comment / review / issue                                            | addresses it, pushes to the PR branch; still gated like anyone's commit                                                                                                                                                                             |
| `ci-triage.yml`     | `CI` failed on a PR                                                                | three-line triage comment, read-only                                                                                                                                                                                                                |

**`sdlc.json` `claude: false` turns all three Claude workflows off** — adopt writes none of
them and removes existing ones; `merge-gate` then does not
exist, so leave it out of the ruleset. Flip it back to `true` and re-run adopt when the
`ANTHROPIC_API_KEY` and the model are proven on one PR.

All degrade to green-with-`::notice::` when a secret is absent. `merge-gate` is a
required check while `claude` is on. A review costs money on every run, so it runs once per PR and then only
on the label: fix everything, push, label, merge — not push, wait, push, wait. A PR that changes `claude-review.yml` gets no Claude review (a PR cannot
rewrite its own reviewer); read that one yourself before it merges.
