# Evaluator 2: navigation, layout, surfaces, states

Snapmark v0.9.0 (frozen copy of `main`), audited 2026-09-28. Checks C5, C6, C9, C16; rule areas navigation and
return, side panels and detail pages, dialogs, menus and popovers, feedback and notifications, progress and long
operations, local work and external writes, remembered state, first run and help, motion; the checklist's
navigation section; the briefing's question 3 (capturing from a full-screen app).

How it was seen: the real editor, session window and area picker through the audit harness and my own Electron
scripts on the mock "Acme Ops" page, each with its own temp `SNAPMARK_ROOT` and `userData`. The menu bar menu,
the capture overlay, notifications, native dialogs, the Dock and Spaces were read in the code. No full-screen
window was created. Screenshots: `../shots/2-*.png`.

## Findings

### Question 3: capturing from a full-screen app

The short answer, read in the code and matching the owner's report: the capture itself works on the full-screen
browser's Space, and so does the area picker. The editor does not. Snapmark opens the editor window while it is
still a menu-bar-only app, which lets the window sit on the browser's full-screen Space; in the same moment it turns
itself into a Dock app and pulls itself to the front, and macOS answers that by sliding to the desktop. The
reviewer lands on the desktop and the editor stays behind on the browser's Space. After saving, the editor closes
where it is, so the reviewer ends on the browser only if they went back to find the editor. Findings 2-01 to 2-05.

### 2-01 · Capturing from a full-screen browser sends you to the desktop and leaves the editor behind

- **Impact:** High: every reviewer who reviews a build in a full-screen browser loses the editor after each
  capture and has to go and find it, on the main scene's most frequent path.
- **Current experience:** The reviewer has Chrome in full screen, presses ⌃⇧1 and drags a region. The Mac slides
  to the desktop, which shows no editor. The editor is open, but on Chrome's full-screen Space, where the reviewer
  just was. They swipe back (three fingers, or ⌃→), find the editor over the browser, mark, press ⌘↵, and are back
  on the browser. One capture costs a Space trip out and back, and the first time it looks as if the capture failed.
- **Visual:** `2-fullscreen-today.png` (a diagram of the two Spaces from the code and the owner's report, not a
  screenshot: no full-screen window was created) and `2-fullscreen-proposal.png` (labelled "Proposal").
- **Recommendation:** Open the editor on the Space where the capture was taken, the way the area picker already
  does: create it as a window that may appear over a full-screen app, and do not switch Snapmark into a Dock app at
  that moment. When the editor closes, the reviewer is still on the browser, where they started. The Dock icon can
  follow once the reviewer is on a normal desktop, or be skipped over full-screen Spaces, where the Dock is hidden
  anyway.
- **Tradeoff:** A window allowed over full-screen apps follows the reviewer to every Space until it is closed (the
  area picker's setting), unless it is pinned back to its Space after it opens, which needs a check on macOS; and
  the owner's Dock icon would not appear while the editor sits over a full-screen app. Alternative: open the editor
  on the desktop on purpose and bring the reviewer back to the browser's Space after "Add to session"; that keeps
  the Dock icon but costs two Space slides per capture.
- **Decision needed:** Should the editor open on top of the full-screen browser (no Dock icon while it is there), or
  on the desktop with Snapmark taking you back to the browser after you add the screenshot?
- **Verified:** read in the code, plus the owner's report and the stand-in test the audit lead ran (macOS showed the
  desktop while the editor was not on the visible screen). Not reproduced here: no full-screen window was created.
- **Owner's words:** "When I take a screenshot it's going to the desktop but the actual window stays at the full
  screen browser. This is something we should fix." — 2026-09-28; "For whatever reason in full screen mode, the app
  switches to the desktop but the actual window stays where I took the screenshot." — 2026-09-28. On the Dock
  icon: "when the window is open there's no icon or anything at the bottom to show that it's open." — 2026-09-25

## Rule areas: today's behaviour and a proposed default

Build audited: main at v0.9.0 (the only build in scope). Every proposal is `status: proposed`; none is accepted.

### Navigation and return

- **Today:** the menu bar menu is the only hub. Each capture opens its own editor, centred, exactly over any editor
  already open. Saving or discarding closes the editor and leaves the reviewer wherever macOS puts them; from a
  full-screen app the editor is stranded on that Space while the Mac slides to the desktop. The session window is
  reached only from the menu; Edit Again opens an editor over it and closing returns to it. No window lists or
  links to another; the editor cannot reach its session. Opening a session window or the Keyboard Shortcuts window
  that is already open brings it forward (good).
- **Proposed default:** the reviewer ends where they started. When an editor closes, added or discarded, the reviewer
  is on the app and Space they captured from. Every Snapmark window names what it holds in its title (session and
  entry) and links to its session. Opening anything already open brings it forward.
- **Exceptions:** the session window may open on the desktop, because it is a place to read, but the Mac then goes
  there with it (2-05).
- **Applies to:** editor, session window, area picker, Keyboard Shortcuts window. **Findings:** 2-01 to 2-05, 2-20,
  2-21, 2-24, 2-32.

### Side panels and detail pages

- **Today:** the editor's right panel (320 px, always shown) holds the comment and the references; cards and moves are
  missing; the buttons stay pinned while the notes scroll. The session window is the session's detail page with two
  views, Document and Screenshots, that keep separate positions and separate actions.
- **Proposed default:** the editor's panel is the whole text of the screenshot (comment, references, cards, moves), each
  line linked to its mark, with the target session and the buttons in the pinned footer. The session window has one
  "current entry" shared by both views, and each entry's actions sit beside the entry.
- **Exceptions:** none.
- **Applies to:** editor, session window. **Findings:** 2-22, 2-25, 2-51, 2-52, 2-53.

### Dialogs, menus and popovers

- **Today:** one Snapmark dialog (the quit question); three macOS Open panels (Sessions Folder…, Other Session…, Reopen
  Discarded…) with the default "Open" button; a script dialog for Rename; no confirmation before Discard or Remove
  (both recoverable). The Mac menu bar shows Electron's stock menus.
- **Proposed default:** interrupt only to protect work that has no way back: quitting or restarting with unsaved
  editors, closing Edit Again with changes. Everything recoverable happens at once and offers Undo where it happened.
  Dialogs are Snapmark's own, attached to the window they concern; buttons name the action ("Quit", "Restart", "Move
  Sessions"); Esc is the safe choice, Return the default. Open panels carry a message and a button that names the
  action. The Mac menu bar carries the front window's commands.
- **Exceptions:** macOS's capture overlay and permission prompts are the system's.
- **Applies to:** quit and update, Sessions Folder…, Other Session…, Reopen Discarded…, Rename Session…, the Mac menu
  bar. **Findings:** 2-07, 2-10, 2-11, 2-12, 2-14, 2-47, 2-48.

### Feedback and notifications

- **Today:** notifications for New Session, copies, a restored screenshot, wrong folders, a missing session, a taken
  shortcut, update checks and failed exports; nothing at all for Add to session, Discard, Remove from Session or
  Switch Session; failures inside the editor and the session window are silent; errors exist only as notifications.
- **Proposed default:** feedback in proportion, and in place. A frequent success gets a glanceable sign that does not
  interrupt (a count or tick on the menu bar icon). A discard or remove says where it went, with a way back, once.
  A failure shows where it happened and stays until resolved (editor footer, a line in the menu, a bar in the session
  window), in event · consequence · action words. Notifications are for things that happen out of sight and are
  never the only copy of an error.
- **Exceptions:** Copy Prompt for AI keeps its notification (the clipboard cannot show anything).
- **Applies to:** every surface. **Findings:** 2-08, 2-13, 2-23, 2-26, 2-34, 2-35, 2-36, 2-37, 2-38, 2-39.

### Progress and long operations

- **Today:** almost nothing is long: the editor shows its capture 0.2-0.6 s after opening; export of 12 screenshots
  takes 0.3 s (PDF) and 0.02 s (ZIP); the picker waits 0.2 s before capturing. The one long job, the update
  download, says "Downloading…" and then nothing.
- **Proposed default:** under a second, show nothing; over a second, show progress on the control that started it
  (the menu item reads "Exporting PDF…" and is disabled) and say when it is done. A job that can partly fail (moving
  sessions, 2-50) reports what moved and what did not.
- **Exceptions:** none.
- **Applies to:** export, update, sessions folder change. **Findings:** 2-38, 2-50.

### Local work and external writes

- **Today:** Snapmark writes session.md, `img/`, `.edit/`, `.discarded/`, exports in the session folder, and the
  clipboard. Others write session.md too (an agent, the Markdown app, a sync service): the session window reloads in
  place, and typing made at that moment is dropped. A save into a folder moved away fails silently. Changing the
  sessions folder leaves sessions and Discarded behind. The session window loses the last keystrokes on close.
- **Proposed default:** the reviewer's words are never dropped. A write that collides keeps the reviewer's text and
  asks; a write that fails says so in place with a way forward; a change from outside shows in place (as today).
  Moving the sessions folder offers to move the sessions. Closing a window writes what it holds first.
- **Exceptions:** none.
- **Applies to:** session window, editor, Sessions Folder…. **Findings:** 2-08, 2-09, 2-18, 2-19, 2-50.

### Remembered state

- **Today:** remembered across launches: the current session, the sessions folder, when each session was last used
  (Switch Session's order), the area. Not remembered: the tool and colour between captures, the session window's tab,
  size, position and entry, the Keyboard Shortcuts window's size. Discarded items: 7 days.
- **Proposed default:** remember what a run of captures repeats (the last tool group and colour, for the running app),
  and what the reviewer arranged per window (size, position, tab; the last entry shown per session). Global, except the
  entry, which is per session.
- **Exceptions:** never start a new capture on a destructive tool variant (Remove area) by memory.
- **Applies to:** editor, session window. **Findings:** 2-43, 2-44.

### First run and help

- **Today:** the first launch shows only the menu bar icon. The Screen Recording permission is explained only in the
  README. Help is the tooltips, the key under each tool, the picker's hint and the Keyboard Shortcuts window under
  Settings; there is no Help menu and no key for help.
- **Proposed default:** the first launch says, once, where Snapmark lives and the two capture keys. A missing permission
  is caught before a capture is wasted, with the steps to fix it. Help is one key away everywhere (⌘/) and in the Mac
  menu bar's Help menu; the shortcut list opens on the keys used most.
- **Exceptions:** none.
- **Applies to:** first launch, first capture, editor, Keyboard Shortcuts window. **Findings:** 2-07, 2-29, 2-30,
  2-40, 2-41, 2-42.

### Motion

- **Today:** Snapmark's own pages have no animation (no CSS transitions or animations). The motion the reviewer sees is
  macOS's: windows opening and closing, and the Space slide when an editor or session window opens from a full-screen
  app (2-01), which moves the reviewer away from their work.
- **Proposed default:** no decorative motion. Motion only to explain a change of place, never to move the reviewer
