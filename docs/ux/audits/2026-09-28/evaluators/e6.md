# Evaluator 6: every lens on the whole app

**How I looked.** I walked the main scene (reviewing an overnight build: ten screenshots in a row, handed to
Claude Code) twice: once as a first-time user who has never read the README, once as a frequent user who
knows every key. I ran the real editor, session window and area picker on the mock "Acme Ops" page with the
audit harness and with my own Electron script that sends real key and mouse events (Esc, typing, clicks), and
looked at every screenshot I cite. The menu bar menu, macOS's capture overlay, notifications, native dialogs,
Spaces (full-screen apps), the Dock icon and first run cannot be scripted: I read them in the code and built
the menu from its own data for four states. Those findings say "read in the code".

**Lenses.** Every finding names its Nielsen heuristic, and where they apply Shneiderman's rules, the Laws of
UX, Maze's lenses, the six plain questions and the writing rules, in its supporting notes. The lens coverage
tables come after the findings.

**Independence.** I read the briefing, setup, owner's words, the shared references, the code and the README.
I did not read any earlier audit, the guidelines, sitemap, glossary proposal, decision files or any other
evaluator's notes.

Screenshots are in `../shots/6-*.png`. Annotation colour is blue, which is never a mark colour.

# Findings

## Global shortcuts and sessions

### 6-01 · A slip onto ⌃⇧2 quietly moves the rest of the review into a new session

- **Impact:** High — the reviewer in the main scene, who fires ⌃⇧1 and ⌃⇧3 dozens of times, starts a new
  session by brushing the key between them, and every capture after it lands in the wrong session.
- **Current experience:** ⌃⇧1 captures a region, ⌃⇧3 captures the same area, and ⌃⇧2, between them, starts
  a new session and makes it current. The only sign is a macOS notification, "New session: 2026-09-28 14.03",
  which fades after a few seconds and names the session by a time stamp the reviewer never chose. Nothing in
  the next editor says the target changed except a grey "→ 2026-09-28 14.03" in the top-right corner. There
  is no undo.
- **Visual:** read in the code; no screen. The mis-press path:

  | Step | What the reviewer does                        | What happens                                                                             |
  | ---- | --------------------------------------------- | ---------------------------------------------------------------------------------------- |
  | 1    | Reviewing, 6 screenshots in "Checkout review" | —                                                                                        |
  | 2    | Reaches for ⌃⇧3, hits ⌃⇧2                     | new empty session created and made current; notification "New session: 2026-09-28 14.03" |
  | 3    | Presses ⌃⇧3 four more times, saves each       | screenshots 7–10 go to the new session as its 1–4                                        |
  | 4    | Copies the prompt for Claude Code             | the prompt points at the new session: four screenshots, not ten                          |

- **Recommendation:** take the global shortcut off New Session. Starting a session happens once per piece of
  work and is not an "on the fly" action; the menu item is enough, and the first capture into a fresh
  session could offer it instead. If the owner wants a key, give it one that is not a neighbour of the
  capture keys and not on the same chord (for example ⌃⇧0 or ⌃⇧N), and put an Undo into the notification
  ("New session started · Undo") so a slip costs one click. This frees ⌃⇧2 for Capture Same Area, so the two
  capture keys sit side by side.
- **Tradeoff:** no instant key for a new session; a reviewer who starts many short sessions a day goes
  through the menu. The Undo alternative keeps the key but still needs the reviewer to notice the
  notification before capturing again.
- **Decision needed:** Should New Session keep a global shortcut at all, and if so, which key away from the
  capture keys?
- **Verified:** read in the code.
- **Owner's words:** "Also the new session is a very dangerous shortcut because it sits in between 1 and 2."
  — 2026-09-28. "This is also important: when I create, as I said, it needs to be shortcuts so I can just do
  this on the fly." — 2026-09-25

- Where: global shortcuts; menu item "New Session"; v0.9.0.
- Broken: Nielsen 5 error prevention, 3 user control and freedom (no undo); Shneiderman error prevention and
  easy reversal; Laws of UX: Fitts's law (the rare, costly target is the closest neighbour of the frequent
  ones), Pareto principle (the key layout favours a rare action), serial position; Maze: limitations in the
  journey.
- Code: `src/main.ts:31-33` (keys), `:110-116` newSession, `:585-592` registration; `src/menu.ts:113`.
- Screenshots: none (global shortcuts cannot be scripted safely).
- Other products: macOS Screenshot keeps ⌘⇧3/4/5 all as capture variants, nothing destructive between them;
  CleanShot X and Shottr have no global key that changes where captures go.
- Seen by: Nielsen, Laws of UX.

</details>

### 6-02 · A screenshot in the wrong session cannot be moved to the right one

- **Impact:** Medium — anyone who captured into the wrong session (after 6-01, or after forgetting to switch)
  has no way to put those screenshots where they belong; the review stays split across two files.
- **Current experience:** the session window offers "Edit Again" and "Remove from Session" for each
  screenshot, and the menu offers "Switch Session". None of them moves a screenshot. "Remove from Session"
  sends it to Discarded, and "Reopen Last Discarded" puts it back into the session it came from, not the
  current one. An open editor keeps saving into the session it was opened for, even after Switch Session.
- **Visual:** read in the code. Proposal (words only): in the session window's Screenshots tab, a "Move
  to…" button beside "Remove from Session", listing the recent sessions; in the editor, the "→ session"
  label becomes a small pop-up to change where this screenshot goes before saving.
- **Recommendation:** add "Move to Session…" for a saved screenshot, and let the editor change its target
  before saving. Both repair a slip without Finder or hand-editing Markdown.
- **Tradeoff:** one more button and one more list to keep in sync; moving renumbers the screenshot in its new
  session.
- **Decision needed:** Should a screenshot be movable between sessions, from the session window, the
  editor, or both?
- **Verified:** read in the code.
- **Owner's words:** "It needs to be some sort of project or session. If there's an existing session I just
  add to the existing session or I create a new session." — 2026-09-25

## Menu bar menu

### 6-05 · Two copy items do one job, and neither label says what lands on the clipboard

- **Impact:** Medium — every reviewer handing a session to Claude Code must choose between "Copy Prompt for
  AI" and "Copy session.md Path" without seeing either result, although the first already contains the second.
- **Current experience:** under "Current Session" the menu lists "Copy Prompt for AI" and "Copy session.md
  Path" one under the other. The prompt's first line is the path ("Work through the visual feedback in
  "…/session.md"."), followed by what each mark means. The path alone gives an agent a file whose marks it
  cannot decode, because `session.md` itself carries no legend. The notification after copying says "Prompt
  for 28 Sep 14.03 copied. Paste it into your AI agent." but never shows what was copied.
- **Visual:** `6-menu-built-vs-proposal.png`, left: the two items at positions 3 and 4 under the session
  header; right, labelled Proposal: one item, "Copy for AI Agent", with the sublabel "Prompt with the path to
  session.md".

  | Where        | Before                                                         | After                                                                                                         |
  | ------------ | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
  | Menu         | "Copy Prompt for AI" + "Copy session.md Path"                  | "Copy for AI Agent" · sublabel "Prompt with the path to session.md"; holding ⌥ turns it into "Copy Path Only" |
  | Notification | "Prompt for 28 Sep 14.03 copied. Paste it into your AI agent." | "Copied: the prompt for 28 Sep 14.03 (7 screenshots) with its path. Paste it into Claude Code."               |

- **Recommendation:** one visible copy item, named for what it copies, with the path-only copy as the ⌥
  alternate. I weighed the owner's idea of one "Copy Session Info" with a Settings choice of with or without
  the prompt: it removes an item, but the label then no longer says what is copied, which depends on a setting
  chosen once and forgotten; that is the confusion the owner described on 2026-09-26. A sublabel that states
  the content answers "copy what?" in the menu itself.
- **Tradeoff:** ⌥ alternates are invisible; a reviewer who wants only the path has to know about ⌥ or delete
  the prompt lines after pasting. The Settings alternative is discoverable once but hides the content at the
  moment of copying.
- **Decision needed:** One copy item that always copies the prompt with its path (path-only behind ⌥), or one
  item whose content is chosen in Settings?
- **Verified:** read in the code; the menu drawn from its own data.
- **Owner's words:** "I just wonder whether we need just "Copy session info" when it comes with the prompt
  and everything, and in the settings you select whether you want to have the prompt with it or without it."
  — 2026-09-28. "The interface doesn't make sense. "Copy for AI," "Copy Paste," "Copy what?" It's not clear
  what's getting copied." — 2026-09-26. "I want to be able to copy and paste the path to the Markdown from the
  current session." — 2026-09-25

## Capturing: Capture Screenshot, Capture Same Area, the area picker, full screen

### 6-13 · From a full-screen browser, the editor pulls the reviewer out to the desktop

- **Impact:** High — the main scene is often reviewed in a full-screen browser; every capture throws the
  reviewer onto another Space, and after saving they have to find their way back before the next capture.
- **Current experience:** macOS's own capture overlay (⌃⇧1) and Snapmark's area picker (⌃⇧3 the first time)
  both work over the full-screen browser; the picker is made to stay on the full-screen Space. The editor is
  not: it opens as an ordinary window, which macOS cannot put on another app's full-screen Space, so the
  screen slides to a desktop Space to show it while the browser stays behind on its own Space. After "Add to
  session" the editor closes; nothing sends the reviewer back to the browser. If they press ⌃⇧3 before
  swiping back, Capture Same Area captures the same rectangle of the desktop, not the page.
- **Visual:** read in the code; Spaces cannot be scripted. The path:

  | Step                          | Reviewer's screen                                                                                               | Editor                            |
  | ----------------------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------- |
  | ⌃⇧3 in a full-screen browser  | browser, full screen                                                                                            | —                                 |

# The briefing's four questions, answered

**1. New Session on ⌃⇧2.** A mis-press between ⌃⇧1 and ⌃⇧3 creates a session and makes it current; every
capture after it goes there until the reviewer notices, and there is no undo and no way to move the
screenshots back (6-01, 6-02). With an empty current session it silently does nothing, in a confusing
sentence (6-03). Starting a session is a once-per-review act that does not need an "on the fly" key: my
recommendation is no global shortcut, New Session inside Switch Session, and ⌃⇧2 given to Capture Same Area
so the two capture keys are neighbours (6-01, 6-06). If a key stays, it must be away from the capture chord
and its notification must carry Undo.

**2. The menu.** Up to 16 top-level items, a header, three submenus, and items that appear and disappear
(6-06, 6-07). Earn their place: the two captures, Open Session, one copy item, Export, Switch Session,
Settings, Quit. Do not: Copy session.md Path as a separate item (6-05), Rename and Show in Finder at the top
level, Reopen items in the first group (6-08), Keyboard Shortcuts inside Settings (6-09). On "Copy Session
Info" with a Settings choice: it cuts one item but hides what is copied behind a setting, which is the
confusion the owner described; one item that always copies the prompt (it already starts with the path),
with a sublabel saying so and path-only behind ⌥, answers "copy what?" in place (6-05). Proposal drawn in
`6-menu-built-vs-proposal.png`: about ten items in four groups.

**3. Capturing from a full-screen app.** Capture Screenshot's overlay and the area picker stay on the
full-screen Space; the editor does not, so the reviewer is moved to a desktop Space for every capture, and
after saving is left there (read in the code; the "after" part is an assumption). A ⌃⇧3 pressed before
swiping back captures the desktop (6-13). Capture Same Area also captures Snapmark's own editor when it is
still open over the area (6-14), and every capture stops for the editor (6-15).

**4. "Not very intuitive."** A first-time user cannot tell what happened at first launch (6-20), gets a
wallpaper capture without explanation (6-19), meets icons whose key captions are tiny (6-38), a key that
switches the tool it shows (6-24), a reference that covers its target (6-27), an Esc that throws the work away
(6-22), two ways to write a note (6-29), a save with no sign of success (6-64), and help filed under Settings
(6-09). The six plain questions per surface are below.

# Did not run

- **The menu bar menu, notifications, native dialogs (Sessions Folder…, Other Session…, Reopen Discarded…,
  Rename Session…, Quit with unsaved work), the Dock icon, Spaces and first run** could not be scripted under
  the safety rules. I read them in the code and drew the menu from its own data (`6-menu-built-vs-proposal.png`
  is a drawing, labelled as such). Findings on them say "read in the code".
- **Where the reviewer lands after saving from a full-screen Space** (6-13): not checked; stated as an
  assumption.
- **The area picker while dragging:** the harness's scripted drag produced a "3 × 0" size label at the far
  right of the screen and an area far larger than the drag (`AREA_RESULT` 571 × 380 for a 300 × 200 drag),
  most likely because the input events and the display's scale or pointer position disagree on this machine. I
  did not report it as a product problem and did not use `6-area-dragging.png` as evidence.
- **Figma and Chrome shortcut clashes with ⌃⇧1–3:** not checked; I did not open those apps.
- **The macOS colour panel** (6-41): not opened; the claim that a colour input opens it is an assumption.
- **PDF with a really tall screenshot:** my "tall" capture was limited by the window to 1600 × 2040 pixels and
  fitted on one page; splitting across pages was not exercised.
- **1440 and 1920 wide editor windows:** not captured; I ran the minimum 1180 × 600 in light (2×) and dark
  (1×). The toolbar fits on one line at the minimum.
- **Contrast values and keyboard-only operation** are left to the accessibility evaluator; I only noted the
  small key captions (6-38).
- **Auto-update and the DMG:** read in the code and README only.
- **The harness's text-insertion helper** failed with a Milkdown error when the note contained `**` (the note
  was lost in that run). A real keyboard types such notes correctly (checked with real key events), so this is
  a harness limit, not a product finding; 6-59 is about what the app does with an empty note either way.
- **Scrolling capture:** exploration for agent 1, not evaluated here.
