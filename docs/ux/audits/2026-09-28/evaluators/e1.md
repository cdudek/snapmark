# Agent 1 · Concepts and structure · Snapmark v0.9.0

Checks: C1 concepts, C2 hierarchy, C3 sitemap, C4 jobs to be done, C18 pattern research and the
scrolling-capture notes. Co-owner (structure side) of the briefing's question 2, the menu.

How I looked: the editor, the session window (both tabs), the area picker and the Keyboard
Shortcuts page were run through the harness on the mock "Acme Ops" page and screenshotted
(`shots/1-*.png`). The Keyboard Shortcuts page is the real page built by the app's own function,
opened in a window of mine. The menu cannot be scripted: it is rendered from the app's own menu
data with the app's own icons, labelled on the image as a rendering and never as a screenshot of
macOS. Notifications, native dialogs, Spaces and the capture overlay are read in the code.

Findings are grouped: the menu, global shortcuts and capture, the editor, the session window,
Discarded, the area picker, the Keyboard Shortcuts window, session.md and the prompt, app-wide.

## Findings

### The menu

### 1-01 · The hand-off asks the reviewer to choose between two copy items whose difference cannot be seen

- **Impact:** High · every review ends here (scene 1), and the reviewer has to guess what each item puts on the clipboard.
- **Current experience:** Under "Current Session: 28 Sep 09.14 · 7 screenshots" the menu offers "Copy Prompt for AI" and "Copy session.md Path". Neither shows what it copies. The prompt is 15 lines: one line with the path, then a legend of every mark ("- Cross: remove this."). The path item copies only the path, and `session.md` itself explains no mark, so an agent given only the path has to guess what a hatched box or a dashed outline means. The notification after the path copy says "Path to 28 Sep 09.14 copied.", naming the session, not the file.
- **Visual:** `shots/1-menu-full-annotated.png` (rendered from the menu data, box 1-01). Proposal: `shots/1-proposal-menu.png`.
- **Recommendation:** One item, **Copy for AI**, and no setting. Write the legend once at the top of each `session.md` when the session is created (4 to 6 short lines), so the file explains itself. Copy for AI then copies one line: `Work through the visual feedback in "<path>/session.md".` The path and the prompt become the same thing, and the menu loses a row and a decision. Measured against the owner's idea of "Copy Session Info" plus a Settings choice (with or without the prompt): that also removes a row, but it hides the difference in a setting that cannot be seen at the moment of copying, and a reviewer who shares Snapmark, or forgets what they set, gets a surprise at paste time.
- **Tradeoff:** Every `session.md` carries the legend (about 150 tokens, once per session, the same as the prompt costs today). Sessions made before the change have no legend, and the legend in the file can be edited or deleted by hand. The owner's Settings idea keeps `session.md` pure and lets a power user trim the prompt.
- **Decision needed:** Should the explanation of the marks live in `session.md` itself, so one "Copy for AI" item is enough, or should the menu keep a copy item plus a Settings choice of with or without the prompt?
- **Verified:** read in the code (menu data rendered; the prompt text printed from the app's own function, see the notes).
- **Owner's words:** "I just wonder whether we need just "Copy session info" when it comes with the prompt and everything, and in the settings you select whether you want to have the prompt with it or without it." — 2026-09-28. "The interface doesn't make sense. "Copy for AI," "Copy Paste," "Copy what?" It's not clear what's getting copied." — 2026-09-26. "I want to be able to copy and paste the path to the Markdown from the current session. I just paste it and then I can point the AI to it." — 2026-09-25

### 1-02 · The menu changes shape with the app's state, so "Copy Prompt for AI" moves by four rows

- **Impact:** Medium · the reviewer who reaches for the hand-off by position (scene 1) lands on the wrong row whenever an update waits, an area is set or something was discarded.
- **Current experience:** On a fresh session "Copy Prompt for AI" is the 6th row. Once an area is set ("Choose New Area…" appears), something was discarded ("Reopen Last Discarded" and "Reopen Discarded…" appear) and an update waits ("Restart to Update to 0.9.1" appears on top), it is the 10th row. The whole session block slides down by four rows, and back up after a restart or seven days.
- **Visual:** `shots/1-menu-first-run.png` against `shots/1-menu-full.png` (both rendered from the menu data).
- **Recommendation:** Keep the rows above the session block fixed. Show "Choose New Area…" always (it can read "Choose Area…" before the first time), keep "Reopen Last Discarded" as one always-present row (greyed when there is nothing) lower in the menu, and move "Restart to Update" to the bottom, above Quit. The frequent items then never move.
- **Tradeoff:** A greyed row is visible even when it does nothing; the update line is less prominent at the bottom.
- **Decision needed:** Should the rows above the current session stay fixed, with rarely available items shown greyed or placed lower, instead of appearing and disappearing on top?
- **Verified:** read in the code (menu data for four states dumped and rendered).
- **Owner's words:** "The order of the menu just doesn't make sense." — 2026-09-25

### 1-04 · The three global keys are numbered by history, not by job: New Session sits between the two captures

- **Impact:** High · in scene 1 the reviewer presses ⌃⇧1 and ⌃⇧3 dozens of times; one slip onto ⌃⇧2 silently starts a new session and every following screenshot lands in it.
- **Current experience:** ⌃⇧1 "Capture Screenshot", ⌃⇧2 "New Session", ⌃⇧3 "Capture Same Area". The menu lists them 1, 3 and, eight rows lower, 2; the Keyboard Shortcuts window lists them 1, 3, 2. A mis-press shows only a notification ("New session: 2026-09-28 22.15"). Getting back takes three clicks (menu, Switch Session, the old session), and the empty session it made stays in the Switch Session list for good: Snapmark has no way to delete a session.
- **Visual:** `shots/1-menu-full-annotated.png` (box 1-04).
- **Recommendation:** Give the two capture actions the neighbouring keys (⌃⇧1 capture, ⌃⇧2 capture same area) and take New Session off the global keys (menu only, or a key far from the digits if the owner wants one). Starting a session happens once per review. Capturing happens on every screenshot, so it earns the keys.
- **Tradeoff:** ⌃⇧3 moves to ⌃⇧2 one day after it shipped, so the owner re-learns one key. New Session without a key costs one menu trip per review.
- **Decision needed:** Should New Session lose its global key, with Capture Same Area moving to ⌃⇧2?
- **Verified:** read in the code (keys, menu order, the notification, no delete action). Pressing the real keys is not allowed in this audit.

### 1-09 · Every session action works only on the current session, so acting on an older one silently redirects the next captures

- **Impact:** Medium · to copy, export, rename or open an older session, the reviewer must first make it current, and then forgets to switch back: the next screenshots of today's review land in last week's session.

"Open Session", "Copy Prompt for AI", "Copy session.md Path", "Rename Session…", "Show Session in Finder" and "Export Session" all act on the current session. Handing yesterday's session to an agent takes five clicks (menu, Switch Session, the session, menu, Copy Prompt for AI) and leaves yesterday's session as the one new captures go into.

**Named or reachable two ways**

- The editor: from ⌃⇧1, ⌃⇧3, Choose New Area…, Reopen Last Discarded, Reopen Discarded… and Edit Again. Six entries, one window. Only Edit Again changes its button ("Save changes"), and a reopened Edit Again loses it (1-26).
- The session window: Open Session, and restoring a removed screenshot opens it too.
- "Discard" (editor) and "Remove from Session" (session window) lead to one store; "Reopen" brings back both, with different results (1-25).
- "Capture Screenshot" and "Capture region" are one action (1-30); the session's name has two forms (1-16).
- Finder is reached three ways (Show Session in Finder, export, the two folder choosers), and none of them from the session window.
- Discard is reached four ways: ⌘W, the button, Esc past Select, the close button.

**Dead ends and no way back**

- Editor → session: the editor cannot open its session or change where it saves (1-21); after saving, nothing points to where it went.
- Session window → hand-off, export, rename: only through the menu, only for the current session (1-08, 1-09).
- Any non-current session: reachable only by making it current, which redirects the next captures (1-09).
- Sessions left in a previous sessions folder: unreachable (1-10). Sessions: no delete (1-32).
- A taken global key: no way to choose another (1-11).
- Discarded, beyond the last item: a folder chooser (1-28).
- The Keyboard Shortcuts window: one path only (Settings), none from the editor (1-07).
- After a capture from a full-screen app: the reviewer is on the desktop, the editor on another Space (1-13).
- The saved area: cannot be seen or cleared (1-15).
- First launch: no window, no hint; only the menu bar icon (agent 2's first-run area).

## Scrolling capture: exploration notes

Notes for a later decision, not findings. The owner: "Is this possible without it being a Chrome
extension or something? It's not important. This shouldn't be the default. We just want to maybe
explore this." — 2026-09-28

**How others do it (from memory; details unverified)**

- CleanShot X "Scrolling Capture": the reviewer selects an area, presses Start, then scrolls (or turns on auto-scroll); CleanShot captures frames and stitches them by matching overlapping rows. Auto-scroll posts scroll events and needs the Accessibility permission. Known trouble: sticky headers and footers, lazy-loaded content, animated content. Works in any app, not only browsers.
- Shottr "Scrolling screenshot": select an area, scroll manually (auto-scroll exists in newer versions, unsure), Shottr stitches; it trims repeated fixed headers. Any app.
- macOS Screenshot: no scrolling capture. Safari and Chrome can save a whole page without an extension: Chrome DevTools command menu "Capture full size screenshot", Firefox's built-in screenshot "Save full page".
- Xnapper: no scrolling capture that I know of. Figma: not applicable.

**What Snapmark would need, without a browser extension**

- Permission: Screen Recording, which Snapmark already has. Auto-scroll would add Accessibility (posting scroll events), a second, more alarming permission prompt, plus a native helper, because Electron has no API to post global scroll events.
- Frames: `screencapture -R` per frame starts a process each time (about 100–300 ms, a guess), fine for manual scrolling at the reviewer's pace. Faster: Electron's `desktopCapturer` stream (same permission, no native code), cropped to the saved area, sampled while the reviewer scrolls.
- Stitching: compare each frame with the last by rows (hash or grey-level correlation), find the vertical offset, append only the new rows. Rows that never change across frames are a fixed header or footer: keep them once. Stop on Esc or a key, and when the offset stays zero.
- It fits Snapmark's own model: Capture Same Area already defines the rectangle; "Scroll Capture Same Area" would reuse it.
- Limits: sticky or parallax elements, lazy loading and skeletons, carousels and animations, scroll-snapping, virtualised lists (rows recycled while scrolling), horizontal scroll, very long pages (memory).
- The editor would need zoom and scrolling first: today it fits the whole image into the window, so a 1280 × 8000 page would show about 100 points wide.

**Cost for the AI**

- Snapmark already shrinks every image to at most 1568 px on the long edge and about 1.15 megapixels (Claude's own limits). A 1280 × 8000 page shrunk that way is about 250 × 1568: unreadable.
- Claude counts roughly width × height ÷ 750 tokens per image, so a readable long page must be cut into tiles of about 1.15 megapixels each, about 1,500 tokens per tile. A 1280 × 8000 page is about 10 megapixels, 9 tiles, about 14,000 tokens, against about 1,500 for one screenshot of the viewport.
- Tiles fit `session.md` as they are: one entry per tile ("## 004a · …", "## 004b · …"), marks per tile.

**Options, cheapest first**

1. Do nothing new: the reviewer already can do "Capture Same Area, scroll, Capture Same Area" (two keys per viewport, one entry each), which is tiled and token-honest by construction.
2. Accept an image from outside: "Mark Up Image…" or paste from the clipboard into the editor, so a Chrome "Capture full size screenshot" can be marked and added. No new permission, small code; needs editor zoom for tall images.
3. Manual-scroll stitching over the saved area (`desktopCapturer` frames, row matching, fixed-header trim), saved as tiles. Medium effort, no new permission.
4. Auto-scroll stitching: 3 plus scroll events, Accessibility permission and a native helper. Largest effort and a second permission.
