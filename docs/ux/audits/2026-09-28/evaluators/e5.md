# Agent 5 · Accessibility (WCAG 2.2 AA) · Snapmark v0.9.0 · 2026-09-28

Scope: the editor, the session window, the area picker, the Keyboard Shortcuts window (all run with real
key presses through `webContents.sendInputEvent` in my own Electron scripts, never the real screen) and the
menu bar menu (read in `src/menu.ts` and `src/main.ts`). Method: the `omr-dev:audit-accessibility` skill

## Findings

### Editor

### 5-01 · No mark can be placed, selected, moved or resized without a pointer

- **Impact:** Critical · a reviewer who cannot use a mouse or trackpad (repetitive strain injury, tremor, a switch or keyboard-only setup) cannot mark a screenshot at all, which is the editor's whole job.
- **Current experience:** Tab walks the nine toolbar controls, the comment field, Discard and "Add to session", then starts over; the image is never a stop. Pressing 2 chooses Box, but Enter, Space, the arrow keys and Tab then add nothing (0 marks after six key presses). A mark drawn with the pointer can never be selected by Tab, and with it selected the arrow keys do not move it (its position was identical before and after four presses). Only ⌫ works, and only on a mark the pointer selected first. The Keyboard Shortcuts window lists no key for placing or moving a mark either.
- **Visual:** `shots/5-tab-order-annotated.png` (green: every Tab stop; pink: the image, never reached). Proposal: `shots/5-proposal-keyboard-marks.png`.
- **Recommendation:** make the image one Tab stop with a visible keyboard cursor (a crosshair). Arrow keys move the crosshair (⇧ for 10× steps), Enter places the current tool there at its click size (a plain click already makes a box with the pointer as its top left, so the size exists), and Enter on a second point finishes an arrow, a card's pointer, a cut or a redaction. In Select, Tab and ⇧Tab step through the marks in reading order, arrows nudge the selected mark, ⌥-arrows resize it, ⌫ deletes. Announce each result ("Box 3 placed", "Reference 2 selected"). This also serves the owner's own speed request: marks from the keyboard without reaching for the trackpad.
- **Tradeoff:** a real piece of work (a keyboard cursor layer, focus handling on the canvas, announcements). The quickest partial fix, nudging and resizing a selected mark with the arrow keys, helps pointer users too but leaves placing a mark pointer-only.
- **Decision needed:** Should the editor be fully usable from the keyboard (placing and editing marks), or is a pointer an accepted requirement for Snapmark, stated in the README?
- **Verified:** seen on screen (real key events sent to the editor; mark count and position read before and after).
- **Owner's words:** "This is also important: when I create, as I said, it needs to be shortcuts so I can just do this on the fly." — 2026-09-25

### 5-02 · Choosing a tool from the keyboard throws focus back to the top

- **Impact:** High · a keyboard or screen reader user who presses Enter or Space on a toolbar button loses their place: focus falls to the page itself and the next Tab starts again at Select.
- **Current experience:** With focus on the Reference button, pressing Enter chose Reference, and focus was then on nothing (the page body); a screen reader says nothing. The next Tab landed on Select, the first button. The same happens with Space on Box (it switched to Ellipse and dropped focus). Every tool change rebuilds the whole toolbar, so the focused button no longer exists.
- **Visual:** `shots/5-toolbar-focus-before.png` (focus ring on Reference) and `shots/5-toolbar-focus-after.png` (after Enter: no focus ring anywhere).
- **Recommendation:** update the existing buttons (icon, label, pressed state, dots) instead of replacing them, so the focused button stays focused after Enter or Space.
- **Tradeoff:** none worth naming; the rebuild exists only because it was the shortest code.
- **Decision needed:** Routine fix: no individual decision needed.

### 5-03 · Resize handles are 4.5 points square

- **Impact:** High · anyone with less than perfect pointer control (and most people on a trackpad) has to hit a 4.5-point square to resize a mark or card; a miss moves the mark instead, or starts a new one.
- **Current experience:** On a Retina screenshot shown at the editor's 1180 × 600 minimum, the image is drawn at about a third of its real size, and the 13-pixel handles are drawn in image pixels, so they end up 4.5 × 4.5 points on screen. The rotate handle above the mark is the same size. They shrink further as the screenshot gets larger.
- **Visual:** `shots/5-handles-annotated.png` (three of the nine handles boxed, zoomed 2.5×).
- **Recommendation:** size the handles in screen points, not image pixels: divide the handle size by the display scale so every handle has at least a 24 × 24 point hit area (it can still be drawn smaller). Consider dropping the rotate handle, which no mark needs.
- **Tradeoff:** 24-point hit areas crowd a very small mark; hide the middle handles on marks under about 60 points, as Figma does.
- **Decision needed:** Routine fix: no individual decision needed.
- **Verified:** seen on screen (handle size 13 × display scale 0.345 = 4.5 points, read from the running editor).
- **Owner's words:** "Help me think about how we can highlight stuff and potentially add UI elements, like being able to add a card and write on the card, so I can actually edit on the screen and drag and drop, size, and so on." — 2026-09-25

### 5-04 · The selection frame and handles are pale blue on white (1.6:1)

- **Impact:** Medium · a low-vision reviewer cannot tell whether a mark is selected, or find its handles, on a light screenshot; a card on white is hardest (1.5:1).
- **Current experience:** A selected mark gets a frame and hollow handles in pale blue (rgb 178, 204, 255), one pixel thick, at 1.6:1 against white and 1.5:1 against a card's yellow. In the screenshot the handles are barely visible even with full vision.

- **Tradeoff:** a strong accent-coloured frame would compete with the red marks; neutral dark grey with a white keyline avoids that.
- **Decision needed:** Routine fix: no individual decision needed.

### 5-05 · The Highlighter disappears on dark interfaces

- **Impact:** High · a reviewer marking a dark screen (a dark-mode app, a dark header or sidebar) gets a highlight that neither the agent nor a teammate can see, so the note it belongs to points at nothing.
- **Current experience:** The Highlighter multiplies yellow into the image at 45%. On the mock's near-black header the result is rgb 24, 22, 16 next to rgb 24, 24, 27: 1.0:1, invisible in the saved image. On white it is a pale yellow at 1.2:1, visible with full vision but faint for low vision.
- **Visual:** `shots/5-marks-backgrounds-annotated.png` (top left: a highlight on the dark header that cannot be seen; bottom: the same highlight on white).
- **Recommendation:** on dark pixels, make the highlight lighten (screen blend, or a yellow fill with a 1-point yellow outline), keeping multiply where the ground is light; or always add a thin outline so the area reads at 3:1 on any ground.
- **Tradeoff:** a lightening highlight over dark text lowers that text's contrast a little; the outline-only option keeps the text intact.
- **Decision needed:** On dark screens, should the Highlighter lighten the area, or keep its fill and add an outline?
- **Verified:** seen on screen (pixels read from the editor's canvas after a real drag).
- **Owner's words:** "Help me think about how we can highlight stuff and potentially add UI elements, like being able to add a card and write on the card, so I can actually edit on the screen and drag and drop, size, and so on." — 2026-09-25

### 5-06 · "Keep" and "remove" are told apart by colour alone

- **Impact:** High · in the quick-verdict scene, a colour-blind teammate reading the PDF (about 1 in 12 men) cannot tell a green "keep" box from a red one, and the agent is told both mean "look at this element"; the verdict is lost.
- **Current experience:** There is no approve mark. To say "keep this" the reviewer picks green in the colour picker and draws a Box, which the prompt explains only as "look at this element", exactly like a red box. In a deuteranopia view of the same screenshot the green box around "Paid" and the red boxes around the buttons are one olive colour. The Cross and Remove area carry their own shapes, so "remove" survives; "keep" does not.
- **Visual:** `shots/5-redgreen-normal-annotated.png` and `shots/5-redgreen-deuteranopia-annotated.png`, side by side. Proposal: `shots/5-proposal-keep-mark.png`.
- **Recommendation:** give "keep" its own shape and meaning: a green tick (or a box with a tick in its corner), with its own line in the prompt ("Keep: leave this as it is"). Red and green then only reinforce a shape that already says it.
- **Tradeoff:** one more tool in a toolbar the owner already finds dense, and the owner dropped the tick once; it can be a third variant on key 5 ("verdict": cross, remove area, keep) instead of a new key.
- **Decision needed:** Should Snapmark have its own "keep" mark (a tick), and on which key?
- **Verified:** seen on screen (real drags; deuteranopia simulated from the screenshot with the Machado 2009 matrix).
- **Owner's words:** "a tick for approving, or kind of like a thumbs up or something for approval in green" — 2026-09-25; later "We don't need to tick and Thumbs Up." — 2026-09-25

### 5-08 · Arrow, Cut & move, Redact and a card's pointer can only be made by dragging

- **Impact:** Medium · a reviewer who can click but not hold and drag (a trackpad with a tremor, head or eye pointer, switch control) cannot draw an arrow, cut and move an element, redact private details, or point a card at something.
- **Current experience:** A plain click with Box, Ellipse, Cross, Remove area, Highlighter or Spotlight makes a mark at a default size, so those have a single-click route. A plain click with Arrow, Cut & move or Redact makes nothing (probe: 0 marks each). A card made by a click has no pointer line, and there is no later way to add one.
- **Visual:** `shots/5-yellow-green-references.png` (the result of one click with each tool: boxes, cross, hatched area, highlight, a spotlight dimming the image; no arrow, cut or redaction).
- **Recommendation:** accept two clicks as the drag: the first click sets the start (show it as a dot), the second sets the end. That gives Arrow, Cut & move, Redact and the card's pointer a click route, and matches the keyboard route in 5-01 (Enter twice).
- **Tradeoff:** a stray first click leaves a pending start point; Esc or a click on the same spot clears it.
- **Decision needed:** Routine fix: no individual decision needed.
- **Verified:** seen on screen (real single clicks with each tool; mark count read before and after).
- **Owner's words:** "Can I drag it around or just move it around with the cursor?" — 2026-09-25

## Accessibility rules the proposed interaction guidelines must include

Each is written so it can be checked; the finding numbers show the evidence.

1. **Every pointer action has a keyboard route** (keyboard and focus). Placing, selecting, moving, resizing and deleting a mark; choosing the capture area; opening the menu. The image is one Tab stop with a keyboard cursor; arrows move, Enter places, Tab cycles marks, ⌥-arrows resize. (5-01, 5-35, 5-45)
2. **Every drag has a click route** (drag and drop). Two clicks stand for press and release: arrows, cuts, redactions, card pointers, the capture area. (5-08, 5-09, 5-36)
3. **Act on release, not on press** (editing). A press that slides off does nothing. (5-43)
4. **Focus never falls to nowhere** (keyboard and focus). A control acted on keeps focus; if it disappears or is disabled, focus moves to a named neighbour; leaving a note or card returns focus to its mark. (5-02, 5-29, 5-44)
5. **Where focus lands when a surface opens**: the editor on the image (once it can hold focus) or the first tool; the session window on the tab it opened with; the area picker on its frame. When a surface closes, focus goes back to where it came from. (focus table above)
6. **Every control and field has a name in words** (dialogs and menus, forms). Icons, arrows and swatches get a spoken name; placeholders never serve as the only name; shortcuts are exposed as key-shortcut properties, not spelled into the name. (5-11, 5-23, 5-26, 5-46)
7. **Every picture has a text alternative, decoration none** (feedback). The image being marked, the screenshot in the Screenshots tab, each mark in a spoken list; icons next to a word are hidden. (5-10, 5-25, 5-41)
8. **Every result is spoken** (feedback). One polite live region per window: tool chosen, mark placed or removed, undo, saved into which session, screenshot n of m, area size. (5-18, 5-30, 5-37)
9. **Contrast in light and dark, measured** (visual). Text 4.5:1 including placeholders and muted greys; states, field edges, focus and selection handles 3:1; marks carry a keyline so they read at 3:1 on any ground; the Highlighter stays visible on dark screens. (5-04, 5-05, 5-07, 5-14, 5-15, 5-16, 5-17, 5-27, 5-28, 5-38)
10. **Meaning is never colour alone** (editing). Every verdict has its own shape (cross = remove, tick = keep), and the prompt names the shape; colour only repeats it. (5-06)
11. **Targets at least 24 × 24 points on screen**, including canvas handles, measured in screen points, not image pixels. (5-03)
12. **Single-key shortcuts stay out of text fields and can be switched off** (keyboard and focus). (5-13)
13. **Every page declares its language; every window title names the task and the session** (platform conventions). (5-19, 5-20, 5-33, 5-39, 5-42)
14. **Usable at 200% zoom; side panels stack at 400%** (side panels). (5-21)
15. **Motion respects Reduce Motion** (motion). Nothing animates today; anything added later is off under `prefers-reduced-motion`.
16. **Native first** (platform conventions). The menu, dialogs and notifications stay native, which keeps them keyboard and VoiceOver accessible without extra work.

**Enforcement map (proposed):** the smoke test already drives every window; add assertions there, because they run on every build: every button and field has a non-empty accessible name (DevTools accessibility tree), `html[lang]` on every page, no `img[alt=""]` on content, a live region exists, the Fabric handle size divided by the display scale is at least 24, focus is on a named control after Enter on each tool button and after Next at the last screenshot, and the token contrast ratios (a table like the one in the checklist) meet their thresholds. axe-core covers names, lang and text contrast; the rest needs the smoke test.

## Did not run

- **A real screen reader session.** VoiceOver was not run (it would speak and move focus on the owner's real screen). Names, roles and states come from Chromium's accessibility tree read through the DevTools protocol, which is what VoiceOver reads; the exact spoken wording in the findings ("leftwards arrow", "edit text") is inferred, not heard.
- **The menu bar menu, notifications, native dialogs and macOS's capture overlay.** Not scriptable and on the real screen; evaluated from `src/menu.ts` and `src/main.ts`. Whether VoiceOver names the menu bar icon "Snapmark" (Electron sets only a tooltip) is an assumption, not checked. The ⌃F8 route to the menu was not tried, because it would open the owner's real menu bar.
- **Capture region (⌃⇧1).** macOS's own `screencapture -i`; pressing ⌃⇧1 is forbidden. Its pointer-only nature is read in the code and noted under 5-35.
- **Text spacing (1.4.12).** Not tested; the fixed 11-point caption row under the tools (`src/editor.html:78`) would likely clip with the WCAG spacing overrides.
- **Session window at 400% zoom, and dark-mode screenshots of the session window.** Dark-mode contrast for the session window is computed from its CSS tokens (the same as the editor's), not sampled from a screenshot.
- **macOS Increase Contrast, Reduce Transparency and larger system text.** Not tested; the pages do not use `prefers-contrast` (read in the code).
- **Focus return from an Edit Again editor to the session window.** Not tested.
- **Non-Retina (1×) handle size.** Computed, not captured: at 1× the display scale is about 0.69, so handles are about 9 points, still under 24.
- **The Skill** `omr-dev:audit-accessibility` was available, loaded and followed (WCAG 2.2 POUR, the manual checklist, automated axe-core pass). Lighthouse was not run: the pages need Snapmark's preload and do not load in a browser.
