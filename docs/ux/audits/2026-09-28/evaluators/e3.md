# Evaluator 3: controls, lists, visual design, window sizes

How this was checked: the real editor and session window, compiled from the frozen build, opened through
`AUD/harness.js` on the "Acme Ops" mock page with a fresh `SNAPMARK_ROOT` per run; my own Electron scripts
(same build, same temp roots) for real input events, Edit Again, the Keyboard Shortcuts window and timings; the
menu built from `dist/src/menu.js` as data. Screenshots are `../shots/3-*.png`; every one cited was opened and
looked at. Coordinates, sizes and colours come from `getBoundingClientRect` and `getComputedStyle` in the running
page. Nothing was written outside temp folders, `../shots/3-*` and this file.

A harness caveat other agents may meet: the harness's `note()` helper types with `execCommand` and blurs in the same
task; a click placed immediately after it (no `await sleep`) rebuilt the References rows before ProseMirror had read
the typing, and the first note was saved as "_(no note)_". With a 150 ms pause it never happened, and real typing
updates the field synchronously, so this is a harness artifact, not a finding.

## Findings

### 3-01 · Red means "remove", and almost every other mark is red too

- **Impact:** High · Anyone reading a marked screenshot, the reviewer in a quick verdict and the agent in an overnight review, cannot tell "remove this" from "look here" by colour, because both are the same red.
- **Current experience:** A fresh editor starts with the colour swatch on red. A box ("look at this element"), an arrow, a reference circle, the stripe and pointer line of a card, and the outline and arrow of a moved piece all come out in the same red as the Cross and Remove area marks. Only Highlighter and Spotlight have their own colours. The app's own main button, "Add to session", and the focus border of every note field are that red as well.
- **Visual:** `3-review-1180-light-red-annotated.png`: one review with every tool; eight red things, two of which mean "remove".
- **Recommendation:** Keep red for the Remove group only. Give every other mark a default that is not red (the swatch then starts on that colour), and move the app's accent (main button, focus border, reference badge) off red as well. An agent then reads red as "remove" without a legend, and the owner's red/green rule holds on the image.
- **Tradeoff:** Red is the most visible colour on most interfaces; a blue default can vanish on blue buttons and links (the mock's "New order" is blue). Orange or magenta avoid both, at the cost of looking less "annotated".
- **Decision needed:** Which colour should marks that do not mean "remove" start in: red as today, or one separate colour (for example orange)?
- **Verified:** seen on screen.
- **Owner's words:** "Also again, we need more elements to be clear about what should go away and what should not." — 2026-09-25

### 3-03 · Selection handles are 4.5 points wide and pale blue

- **Impact:** Medium · A reviewer who wants to resize a mark has to hit a hollow, pale square about the size of a full stop at the editor's default size, so resizing is slow and often misses.
- **Current experience:** Selecting a box shows eight hollow squares and a rotate handle in light blue (rgb 178 204 255). On a Retina screen they measure 4.5 points at 1180 px wide and 8.5 points at 1920, because they are drawn in the screenshot's pixels and shrink with it. A selected reference gets no handles at all, only a thin pale square around the circle (`3-selected-reference-annotated.png`).
- **Visual:** `3-handles-1180-zoom-annotated.png` (enlarged four times).
- **Recommendation:** Draw handles at a fixed on-screen size (about 10 points, whatever the zoom), filled white with a dark outline, so they are visible on any screenshot.
- **Tradeoff:** Larger handles cover more of a small mark while it is selected.
- **Decision needed:** Routine fix: no individual decision needed.

- **Owner's words:** "Help me think about how we can highlight stuff and potentially add UI elements, like being able to add a card and write on the card, so I can actually edit on the screen and drag and drop, size, and so on." — 2026-09-25

### 3-09 · Edit Again silently throws away text fixed in the Document tab

- **Impact:** Critical · A reviewer who corrects a note in the session window's Document tab and later opens the same screenshot with Edit Again loses that correction without any sign, and the agent gets the old text.
- **Current experience:** A screenshot is saved with reference note "Old note". In the Document tab the reviewer types, and session.md now reads "1. Old note (fixed in Document)". They then press Edit Again on that screenshot to move a mark: the editor shows "Old note". "Save changes" rewrites the entry, and session.md reads "1. Old note" again. The comment and card text go the same way.
- **Visual:** `3-probe-doc-edited-annotated.png` (the fix, saved), then `3-probe-editagain-annotated.png` (Edit Again with the old note; Save changes).
- **Recommendation:** Keep one copy of each entry's text. Either Edit Again reads the entry's current text from session.md into the comment and notes before it opens, or the Document tab stops treating an entry's generated text as free text and edits it through the same fields. In both cases the newest words win.
- **Tradeoff:** Reading text back from session.md has to cope with anything the reviewer typed there (a note split into two paragraphs, a deleted number); where it cannot map text to a reference, it must say so rather than guess.
- **Decision needed:** When an entry's text was changed in the Document tab, should Edit Again start from that text (and say so when it cannot match it), or should the Document tab stop allowing edits to an entry's notes?
- **Verified:** seen on screen; session.md read before and after with the real editor and session window (probe script, temp folder).
- **Owner's words:** "Also a full markdown view would be nice. including ideally editable like notion with markdown wyiwyg" — 2026-09-25

## Did not run

- **The menu bar menu, native dialogs (Rename, Other Session…, Sessions Folder…, Reopen Discarded…), notifications and the macOS colour panel**: not scriptable; the menu was built as data from `dist/src/menu.js`, the rest read in the code. Findings 3-32, 3-33, 3-37 say so.
- **The Keyboard Shortcuts window**: its HTML is built inside `main.ts` and not exported, so I rendered it with a script that copies the template line for line and uses the app's own tool list (3-30). Not the app's own window.
- **Dropping a file from Finder on the editor**: Electron cannot synthesise a file drag; 3-35 is an assumption from the missing guards.
- **⌘+ and the Electron default menu in the editor**: not pressed (the harness drives the page, not the app menu); stated as an assumption in 3-41.
- **The capture step itself** (`screencapture`, ⌃⇧1, ⌃⇧3): never run, by the safety rules; the area picker was driven in its own window only. Timings in the performance table start when the editor is asked to open.
- **A real agent reading session.md**: token costs are computed from the resize rule and the width × height ÷ 750 estimate, not measured.
- **PDF and ZIP export**: not exported in my runs; the PDF row in C10 is read in the code.
- **Session window dark at 1440 and editor dark at 1920 or at 1×**: not captured; light and dark were compared at 1180 and 900 × 900 only.
- **Harness caveats**: (1) `note()` followed at once by a click can lose the note (see the top of this file); (2) a screenshot taken right after the last step can show a frame from a moment earlier; every screenshot cited here was checked against the state its step returned, one capture was redone with a longer pause (`3-selected-reference.png`), and one stale capture (`3-viewer-empty-doc.png`) was deleted and redone as `3-empty-session-viewer.png`.
