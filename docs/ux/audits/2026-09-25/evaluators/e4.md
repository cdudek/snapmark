# Agent 4 · Words, vocabulary, keys, earlier requests

Snapmark v0.2.0, `main`. Checks C11, C12, C15, C17; rule areas keyboard and focus, platform
conventions; the content checklist; the glossary proposal.

How the evidence was gathered: the editor was driven through the audit harness at 1180 × 600,
light, Retina, on the mock "Acme Ops" page, with its own temp `SNAPMARK_ROOT` every run. Keys were
dispatched on `document` and on the focused text field; `window.close` was stubbed to count calls
in the text-key run. The menu bar menu, notifications, native dialog, copied prompt and PDF were
read in the code. Screenshots: `shots/4-*.png` (annotated versions end in `-annotated`).

## Findings

### 4-01 · Pressing 5 again for the next marker makes a card instead

- **Impact:** High: in the main scene, a reviewer placing several numbered markers in a row gets an empty sticky card on the second one and loses the rhythm.
- **Current experience:** Press 5, click: marker 1 appears and the button reads "5 Numbered". Press 5 again for the next marker and click: the button now reads "5 Card" and an empty yellow card opens for typing. Pressing a key that is already active cycles to the next tool in the group, so "press 5, click" only works the first time.
- **Visual:** `4-press5-twice-annotated.png`: marker 1 from the first press, an empty card from the second, the button reading "Card".
- **Recommendation:** Pressing the key of the tool that is already active keeps that tool. Cycle with a separate gesture: Shift plus the number, or pressing the key twice quickly. Then "press 5, click" means the same thing every time.
- **Tradeoff:** You asked for "press the same button multiple times … switch between the shapes". Moving cycling to Shift+number or a double press changes that gesture.
- **Decision needed:** When a tool is already active, should pressing its number keep it, with Shift+number to cycle?
- **Verified:** seen on screen.
- **Owner's words:** "When I press the same button multiple times, let's say I have the 1 button, I would switch between the shapes and it would indicate it at the top." — 2026-09-25

### 4-03 · ⌘W throws away the whole screenshot, even while you are typing, and never asks

- **Impact:** High: a reviewer who hits ⌘W out of habit, or while typing in a note, loses the capture, every mark and every note with no way back.
- **Current experience:** ⌘W closes the editor immediately. It is checked before the "am I in a text field" test, so it also fires while the cursor is in "Comment" or in a note. Nothing asks and nothing can be undone. The red close button behaves the same way. The button reads "Discard ⌘W", and the README says "Discard the screenshot".
- **Visual:** harness run `4-textkeys.png`: with "Half-written comment" typed in Comment, one ⌘W keydown on the field called close once (`cmdWInCommentClosed: 1`).

  Proposal (behaviour): ⌘W with no marks and no text closes silently. With marks or text, a sheet asks "Discard this screenshot? Its 3 marks and notes will be lost." with the buttons "Discard" and "Keep editing". The default is Keep editing.

- **Recommendation:** Ask before discarding a screenshot that has marks or text, from ⌘W, the Discard button and the close button alike.
- **Tradeoff:** One extra keystroke for people who really do want to discard.
- **Decision needed:** Should discarding a screenshot that has marks or text ask first?
- **Verified:** seen on screen (the harness counted the close call).
