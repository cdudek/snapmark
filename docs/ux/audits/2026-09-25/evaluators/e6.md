# Evaluator 6: independent heuristic evaluation of Snapmark v0.2.0

Build: `main` at v0.2.0 (`dist/` as built). Editor driven through the audit harness on the Acme Ops mock page;
menu bar menu, capture, notifications, dialogs, exports, first run evaluated from the code. All screenshots are
in `scratchpad/audit/shots/`, prefixed `6-`; annotated versions are `6-a-*.png`.

What I tried to do as the owner: review an "overnight build" screen in one pass: box the header actions,
cross out "Export CSV", tick "New order", three numbered notes, a card pointing at "Load more", highlight a
stat, cut and move an element, a comment, then save and read the resulting `session.md` as an agent would.
Also: two spotlights, three cards, a green box, the Highlight group cycled to Redact, a window narrower than
1180 px, 1920 × 1080, and dark appearance.

## Editor window

### 6-01 · Closing the editor throws away every mark without asking

- **Impact:** High: anyone who presses ⌘W, clicks "Discard" or the window's close button loses the whole annotated screenshot, and there is no way back.
- **Current experience:** After ten minutes of marks and notes, "Discard ⌘W" or the red traffic-light button closes the window at once. The captured image is deleted from the temp folder the moment the window closes, so the screenshot cannot even be recaptured as it was (the build may have changed).
- **Visual:** `6-a-discard.png` (the "Discard ⌘W" button, labelled). Proposal: if the canvas has any mark, a note or a comment, closing asks "Discard this screenshot and its 6 marks? · Discard · Keep editing", with Keep editing as the default; an empty capture closes silently.
- **Recommendation:** Confirm only when there is something to lose. Alternatively keep the last discarded capture for one "Reopen last discarded" in the menu.
- **Tradeoff:** One extra key press when the discard is intended; a reopen item adds a menu entry.
- **Decision needed:** Should discarding a marked-up screenshot ask first, or be undoable from the menu?
- **Verified:** read in the code; the button and its label seen on screen.
- **Owner's words:** "it needs to be shortcuts so I can just do this on the fly." — 2026-09-25

### 6-02 · ⌘W discards the screenshot even while you are typing a note

- **Impact:** Medium: a reflexive ⌘W (close a tab, close a panel) while typing in a note or the comment deletes the whole capture.
- **Current experience:** The keyboard handler checks ⌘W before it checks whether a text field has focus, so ⌘W inside "Note for 2" or "What is this screenshot about?" discards immediately. Everything else in text fields (numbers, Backspace) is correctly left to the field.
- **Visual:** Before: ⌘W in a note field = discard. After (Proposal): ⌘W in a field does nothing, or goes through the confirmation from 6-01.
- **Recommendation:** Treat ⌘W like every other editor key inside a text field, or route it through the confirmation.
- **Tradeoff:** None worth naming.
- **Decision needed:** Routine fix: no individual decision needed (once 6-01 is decided).

### 6-05 · Red means three different things: "look here", "remove" and "moved"

- **Impact:** High: the owner's rule is "remove is always red", but every neutral mark (box, ellipse, arrow, pen, numbered marker, card accent, cut outline) also starts in the same red, so neither a person nor an agent can tell a red box from a remove mark by colour.
- **Current experience:** In one review I boxed the header actions and crossed out "Export CSV": the box and the cross are the identical red, as are the three numbered markers and the outline of the moved piece. The prompt copied for the agent says "Red crosses and hatched areas mean remove", which invites the agent to treat anything red as removal.
- **Visual:** `6-a-red-meanings.png`: A red box ("look here"), B red cross ("remove"), C red marker, D red outline of a moved piece. Proposal: neutral marks default to a colour reserved for pointing (for example blue), red stays exclusive to the Remove group, green to Approve.
- **Recommendation:** Give the neutral groups their own default colour and keep red and green out of the neutral palette (see 6-06).
- **Tradeoff:** Loses the single "Snapmark red" look; users used to red annotation (macOS markup default) may find blue less urgent.
- **Decision needed:** Should red be reserved for "remove" only, with a different default for boxes, arrows and markers?
- **Verified:** seen on screen.
- **Owner's words:** "Also again, we need more elements to be clear about what should go away and what should not." — 2026-09-25
