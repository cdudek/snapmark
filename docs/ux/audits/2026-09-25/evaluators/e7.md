# Evaluator 7: independent heuristic evaluation of Snapmark v0.2.0

Perspective: first a first-time user who installs the DMG and reviews one build, then an expert who
reviews 20 screens in a row every morning. Every lens in `lenses.md` applied to the whole app. The
editor was driven through the audit harness on the mock "Acme Ops" page (light, dark, 1180 × 600,
900 × 600, 1920 × 1080 at 1×). Menu bar menu, capture, notifications, dialogs, exports and first run
were read in the code and the README.

Screenshots (all mine, prefix `7-`) are in `scratchpad/audit/shots/`. Annotated versions end in
`-annotated.png`.

---

## Editor window

### 7-01 · Closing the editor throws away every mark without asking

- **Impact:** High. Anyone reviewing an overnight build loses all marks and notes on a screenshot with one keystroke or one click on the window's close button.
- **Current experience:** "Discard ⌘W", the red window close button and ⌘W all close the editor at once. There is no "Discard 4 marks?" question and no way back: the captured image file is deleted as the window closes. On macOS, ⌘W means "close this window", and people press it by reflex to get a window out of the way.
- **Visual:** `7-review.png`, bottom right: "Discard ⌘W" next to "Add to session ⌘↵". Before: closes at once. Proposal (text): if anything is marked or typed, ask "Discard this screenshot and its 4 marks?" with "Discard" and "Keep editing" (default).
- **Recommendation:** Ask for confirmation only when there is something to lose (at least one mark, note or comment). An empty editor still closes at once.
- **Tradeoff:** One extra keypress for a real discard. The alternative is to keep the last discarded screenshot so it can be reopened from the menu. That's more work, but it never interrupts.
- **Decision needed:** Should discarding a screenshot with marks on it ask first, or be undoable from the menu?
- **Verified:** Read in the code (closing a window could not be scripted safely). Button seen on screen.
- **Owner's words:** "This is also important: when I create, as I said, it needs to be shortcuts so I can just do this on the fly." — 2026-09-25

### 7-02 · When saving fails, the editor goes dead and says nothing

- **Impact:** High. If the session folder was moved, deleted or not yet synced (iCloud, Google Drive), "Add to session" does nothing visible. The user's marks sit in a window that can't be saved.
- **Current experience:** I deleted the session's Markdown file while the editor was open, then clicked "Add to session ⌘↵". The window stayed open and the button stopped working, but it looks exactly as before. There was no message. The error only appears in the developer console ("ENOENT: no such file or directory … session.md").
- **Visual:** `7-savefail-annotated.png`: the button looks clickable but no longer works, and there is no message.
- **Recommendation:** Catch the failure and show it in the panel in plain words, with a way forward: "Couldn't add to the session '2026-09-25 14.02': its folder is missing. [Save to a new session] [Try again]". Turn the button back on.
- **Tradeoff:** A small error area in the side panel that is almost never seen.
- **Decision needed:** When the target session is gone, should Snapmark offer to save into a new session automatically?
- **Verified:** Seen on screen (harness: session.md deleted during editing, then saved).
- **Owner's words:** "Also I wonder what the best way of making this portable is: being able to share this as a PDF or zip it, maybe both. Having it in the cloud." — 2026-09-25

### 7-04 · Pressing 1 in a fresh editor draws an ellipse, not a box

- **Impact:** Medium. Every review session: the first key the user presses gives the second tool of its group, because Box is already active and pressing its key again cycles.
- **Current experience:** The editor opens with "1 Box" highlighted. The README says "`1` Box". I pressed 1 and dragged, and got an ellipse, and the button now reads "1 Ellipse". The same key means "pick" or "next" depending on a state the user didn't set. Returning to a group also picks whatever was used last, not its first tool.
- **Visual:** `7-review-annotated.png`: "Pressed 1 for Box: got Ellipse".
- **Recommendation:** Open the editor with no tool picked, or with Select, so the first press of any number always picks that group's first tool. Alternatively, cycle only when the key is pressed twice within about a second.
- **Tradeoff:** Opening with no tool means one keypress before the first mark. Time-based cycling is harder to explain.
- **Decision needed:** Should the editor open with nothing picked, so 1 always means Box on the first press?
- **Verified:** Seen on screen.
- **Owner's words:** "When I press the same button multiple times, let's say I have the 1 button, I would switch between the shapes and it would indicate it at the top." — 2026-09-25

### 7-05 · The default mark colour is the same red as "remove"

- **Impact:** High. In the quick-verdict scene, and for any agent reading the image, a red box or arrow that only means "look here" looks like a remove mark. Remove is supposed to be "always red".
- **Current experience:** The colour swatch starts at the same crimson the Remove group uses. Box, ellipse, arrow, pen, numbered markers, card stripes and cut outlines are all drawn in it. The active Select and Box buttons are also filled with it. The prompt the menu copies for the agent says "Red crosses and hatched areas mean remove", but a red ellipse around a header sits right next to them.
- **Visual:** `7-review-annotated.png`: red ellipse, red markers and red cross side by side; the Select button filled in the same red.
- **Recommendation:** Reserve red for Remove and green for Approve. Default neutral marks to a colour neither of them uses (for example blue or magenta), and leave red and green out of the colour picker's starting value.
- **Tradeoff:** A new visual identity for pointing marks. Users who pick red by hand can still make ambiguous marks.
- **Decision needed:** Should red and green be kept for remove and approve only, with pointing marks defaulting to a third colour?
- **Verified:** Seen on screen.
- **Owner's words:** "Also again, we need more elements to be clear about what should go away and what should not." — 2026-09-25

### 7-09 · A second spotlight cancels the first, and a spotlight dims marks drawn earlier

- **Impact:** Medium. Pointing at two things with Spotlight produces two grey areas and nothing lit. Cards, ticks and crosses drawn before the spotlight go dark, so the card text becomes hard to read in the saved image.
