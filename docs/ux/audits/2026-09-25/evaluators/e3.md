# Evaluator 3: controls, lists, visual design, window sizes, output for AI

Build: `main` at v0.2.0 (compiled `dist/`). Every screen was captured with the audit harness on the Acme Ops mock page, each run with its own temp `SNAPMARK_ROOT`. Screenshots are in `shots/` with the prefix `3-`. When a screenshot was taken without `THEME`, it shows the machine's dark appearance. The screenshot itself is still light, because the mock page is light.

Checks covered: C7, C8, C10, C13, C14. C19 areas covered: editing, saving and unsaved work, confirmation and undo, lists and selection, forms and validation, undo across the app, copy and paste, drag and drop, search and filters, media playback. Also covered: the output-for-AI check, and the checklist sections for forms, responsive and performance.

## Findings

### 3-01 · Pointing marks use the same red as "remove", so a plain box reads as "delete this"

- **Impact:** High. The quick verdict and the overnight review both depend on red meaning "remove". Every neutral mark (box, ellipse, arrow, pen, numbered marker, card stripe, cut outline) is drawn in that same red by default, so a reviewer or an agent cannot tell "look here" from "take this away".
- **Current experience:** The colour picker starts at the app's accent red. The Remove group uses a fixed red, and the two reds are the same colour value. On a single capture, a red box around an empty area and a red cross over "New order" look like the same kind of mark. The active tool button is filled with that red too, even for Select.
- **Visual:** `3-ann-red-clash.png`: the box ("points at"), the cross ("remove") and the active Select button, all the same red.
- **Recommendation:** Keep red for Remove only. Start the neutral groups in a colour that no fixed-meaning group uses, such as blue or violet, and don't offer red in the picker for them. Use a neutral colour for the pressed state of the tool button.
- **Tradeoff:** Red is the classic annotation colour, and some reviewers expect it. Existing sessions stay red.
- **Decision needed:** Should red be reserved for "remove", with neutral marks starting in another colour?
- **Verified:** seen on screen.
- **Owner's words:** "Also again, we need more elements to be clear about what should go away and what should not." — 2026-09-25

### 3-02 · session.md never says what was crossed out or approved

- **Impact:** High. An agent reading `session.md` cannot tell remove from approve from the text. It has to find the marks in the image, and the only explanation of the colours is in the clipboard prompt, which may never be pasted.
- **Current experience:** In the 10-shot test session, entry 003 has a hatched "Remove area" over the totals column and its only text is "1. Totals should right-align". Entry 002 has a red cross over the Status column and a green tick, and the only text is "Orders table" and "1. Column headers are grey on grey; raise contrast". Entry 004 contains nothing but approvals. The fact that they were approvals appears only because the reviewer typed it into the comment.
- **Visual:** Text of entry 002, before and after:

  | Where                 | Before                                                              | After (proposal)                                                                                                          |
  | --------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
  | session.md, entry 002 | "Orders table · 1. Column headers are grey on grey; raise contrast" | "Orders table · Remove: 1 cross (right third) · Keep: 1 tick (left) · 1. Column headers are grey on grey; raise contrast" |

- **Recommendation:** Write one line per entry that counts the fixed-meaning marks by kind, for example "Remove: 2 (cross, remove area) · Keep: 1 (tick)". Also put the colour legend once, in the `session.md` header, so the file explains itself without the prompt.
- **Tradeoff:** Adds a few tokens per entry. A position word ("top right") is only rough.
- **Decision needed:** Should each entry list its remove and keep marks in words, not only in the image?
- **Verified:** seen on screen. The session.md text was printed by the harness and the images were checked.
- **Owner's words:** "It's basically for providing feedback to AI in a nice and token-efficient way." — 2026-09-25

### 3-03 · Cards appear in session.md with no link to where they are

- **Impact:** Medium. When an entry has several cards, the agent cannot tell which card is about which element without reading the image. A card that points at something loses what it points at.
- **Current experience:** Entry 006 reads "- Card: Rename to Create order" and "- Card: Use the brand blue here". Both cards point at buttons, but the text says neither which button nor that the card points anywhere. Cards are listed in the order they were stacked, and they have no numbers.

- **Decision needed:** Should cards carry a label that the text refers to, as markers do?

### 3-05 · Boxes, arrows, highlights and pen strokes leave no trace in the text

- **Impact:** Medium. Anything the reviewer points at with a box, ellipse, arrow, highlight or pen stroke exists only in pixels. The note that explains it has to sit on a separate numbered marker, and nothing ties the two together.
- **Current experience:** Entry 010 has an arrow pointing at the Edit · Delete column. The text shows only the two markers. Entry 001 has a box around the header actions, and its text mentions only markers 1 and 2.
- **Visual:** `3-session10/010.png` (arrow, no text); `3-session10/001.png`.
- **Recommendation:** Either let a box, ellipse or arrow take a number and a note (the same References row a marker gets), or list those marks in the entry's summary line from 3-02.
- **Tradeoff:** Numbering every shape can clutter the image. Numbering only on request (a modifier key, or a "Number it" action) avoids that.
- **Decision needed:** Should shapes be able to carry a numbered note of their own?
- **Verified:** seen on screen.
- **Owner's words:** "mark something on the screen and then be able to write something in a Markdown doc" — 2026-09-25

### 3-06 · A redaction drawn after a marker hides the marker, but the text still lists it

### 3-10 · Selecting a marker does not show its note, and the note does not show its marker

- **Impact:** Medium. With more than five markers, the reviewer has to match numbers by eye to edit the right note, or to find which disc a note belongs to.
- **Current experience:** In Select mode, clicking marker 1 gives it a faint frame on the canvas. The References row "1" does not change or scroll. Typing in a note does not highlight its disc.
- **Visual:** `3-selmarker.png`: marker 1 selected, its row unchanged.

- **Tradeoff:** Moving focus into the note on select means number keys type into the note until Escape. Highlighting the row without focusing it avoids that.
- **Decision needed:** Should selecting a marker also focus its note, or only highlight the row?
- **Verified:** seen on screen; read in the code.
- **Owner's words:** no earlier request found.

### 3-12 · Selection handles are about 4 px wide and pale, so resizing is guesswork

- **Impact:** High. Resizing a box, card or cut piece is part of the core job ("drag and drop, size"). At the editor's usual size the handles are 4.5 px, on large captures 2.8 px, and they are drawn in a pale translucent blue. A selected card shows only a faint outline.
- **Current experience:** Handle size scales down with the canvas: 4.5 px at 1180 wide on Retina, 5.9 px at 1440, 8.5 px at 1920, and 2.8 px for a 5K capture at 1440. On a small capture the opposite happens: 13 px handles cover a 30 px box completely.
- **Visual:** `3-ann-handles.png` (zoomed, 1180 wide); `3-selcard-zoom.png` (selected card, frame barely visible); `3-ann-small.png` (handles larger than the box).
- **Recommendation:** Draw handles at a fixed on-screen size of about 10–12 px, whatever the zoom, with a solid border and white fill. Give the selected object a clearly visible 1.5–2 px outline.
- **Tradeoff:** Larger handles overlap small marks. Hiding the middle handles on objects under about 40 px solves that.
- **Decision needed:** Routine fix: no individual decision needed.
- **Verified:** seen on screen; sizes measured in the page.
- **Owner's words:** "so I can actually edit on the screen and drag and drop, size, and so on." — 2026-09-25

<details><summary>Supporting notes</summary>

- Code: Fabric's default `cornerSize` 13 in canvas pixels; the canvas is shown CSS-scaled (`src/editor.ts:633-639`), so handles shrink with it.
- Broken: WCAG 2.5.8 target size (24 × 24), checklist accessibility 3, Fitts's law.
- Screenshots: `3-handles.png`, `3-handles-zoom.png`, `3-ann-handles.png`, `3-selcard.png`, `3-selcard-zoom.png`, `3-size-small-1180.png`.

### 3-19 · Discard, ⌘W and closing the window throw away every mark without asking

- **Impact:** High. One slip of ⌘W (right next to ⌘Q and ⌘E) or a click on the red close button loses all the marks and notes on that capture, and the capture file is deleted when the window closes. Nothing can bring it back.
- **Current experience:** "Discard ⌘W" calls `window.close()` straight away. There is no unsaved-work check, no confirmation and no recovery. The temp screenshot is removed on close.
- **Visual:** `3-empty-1180-light.png` (Discard ⌘W beside Add to session). Proposal: when there is at least one mark or any text, ⌘W asks "Discard this capture and its 4 marks? · Discard · Keep editing", with Keep editing as the default. With nothing drawn, it closes straight away.
- **Recommendation:** Confirm only when there is work to lose, as above. Alternatively, keep discarded captures for the session, so they can be restored from the menu.
- **Tradeoff:** One extra key press on a deliberate discard.
- **Decision needed:** Should closing a capture with marks ask first, or should discarded captures be recoverable instead?
- **Verified:** read in the code.
- **Owner's words:** "it needs to be shortcuts so I can just do this on the fly." — 2026-09-25

### 3-22 · Marks cannot be copied, duplicated or pasted

- **Impact:** High. The owner explicitly wants to "copy and paste stuff around". Placing the same card, tick or remove box three times means drawing it three times.
- **Current experience:** With a box selected, ⌘C then ⌘V adds nothing (`D_copyPasteAddsObject: false`). There is no ⌥-drag to duplicate and no Duplicate command.
- **Visual:** none (no change on screen); measured in the page.
- **Recommendation:** Support ⌘C, ⌘V and ⌘D for the selected mark. Paste at a small offset, or under the pointer, and make it undoable. Copying a cut piece copies the piece only, not its ghost and arrow.
- **Tradeoff:** Pasted markers take the next number, which may surprise.

## Did not run

- **The harness cannot build one multi-entry session.** `sessions.create(root, SESSION)` makes "review (2)", "review (3)" and so on when the name already exists. The ten SAVE=1 runs therefore landed in ten folders, and the harness printed only the first `session.md`. I joined the ten entries into `shots/3-session10/session.md`, renumbered 001–010. The real app appends to the active session, so the combined file matches what it would write, apart from the times.
- **Small and very large captures** were simulated. The harness always captures a 1200 × 700 mock window, so the editor's background was swapped in the page, repeating its own init steps (crop or scale, recompute the base stroke, resize the canvas, refit). The window size itself was not recomputed from the image the way `openEditor` does, because W and H were set.
- **Dropping a real file from Finder** (3-24): not possible in the harness; a synthetic drop cannot trigger the browser's default action.
- **Save failure** (3-20), **Discard / ⌘W / window close** (3-19), and the **Switch session** list: read in the code only. Closing the window would end the harness before the screenshot.
- **Clipboard image paste** (3-23): not attempted, because the safety rules forbid touching the clipboard.
- **Real 5K UI text legibility** (3-36): calculated, not seen. The mock was scaled up, so its text stayed readable.
- **PDF rendering of an entry**: not in my checks (agent 2).
- Several screenshots without `THEME` show the machine's dark appearance for the editor UI. That does not affect any finding.
