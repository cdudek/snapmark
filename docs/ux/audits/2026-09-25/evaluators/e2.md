# Evaluator 2: navigation, layout, surfaces, states

Snapmark v0.2.0, `main`. Checks C5, C6, C9, C16, the C19 rule areas navigation and return, side
panels, dialogs and menus, feedback and notifications, progress, local work and external writes,
remembered state, first run and help, motion; and the navigation checklist.

Screens were captured with the audit harness on the mock "Acme Ops" page (1180 × 600, 1440 × 900,
1920 × 1080, 900 × 600, light and dark, Retina). The menu bar menu, notifications, native dialogs,
the capture overlay and first run were read in the code. All shots are in `shots/` with the `2-`
prefix; `-ann` files are the annotated versions.

---

## Findings

### 2-01 · ⌘W and Discard throw away every mark without asking

- **Impact:** Critical. Anyone who presses ⌘W or clicks Discard after marking up a screenshot loses all marks, notes and the screenshot itself, with no warning and no way back.
- **Current experience:** I drew a cross, added marker 1 and typed "important note", then pressed ⌘W. The window closed at once; nothing was written to the session, and the captured image was deleted from disk. ⌘W is the key every Mac user presses to "put a window away", and in this editor it sits next to ⌘Z and ⌘↵, which people also press all the time.
- **Visual:** No screenshot of the closed window can exist, so the evidence is the harness result: 2 objects on the canvas, then "Object has been destroyed", and an empty `img/` folder.
  Proposal (not the real app):
  ```
  ┌ Discard this screenshot? ─────────────────────┐
  │ 3 marks and 1 note will be lost.              │
  │           [Keep editing]   [Discard]          │
  └───────────────────────────────────────────────┘
  (only when something was drawn or typed; an untouched screenshot closes at once)
  ```
- **Recommendation:** When the canvas or any text has changed, ask before closing, with "Keep editing" as the default. An untouched editor still closes at once, so the fast path for a bad capture stays one key.
- **Tradeoff:** One more click when you really do want to throw marks away. The alternative is no dialog but an "Undo discard" route (see 2-04), which is quicker but harder to build in a menu bar app.
- **Decision needed:** Should leaving an editor with marks ask first, or should Discard stay instant and be undoable instead?
- **Verified:** seen on screen (harness run: ⌘W after drawing closed the window, nothing saved, image gone).
- **Owner's words:** "Basically reviewing the designs, doing a complete UX/UI review of an overnight build, providing detailed feedback on different elements." — 2026-09-25

### 2-03 · Quit from the menu bar closes every open editor and loses their marks

- **Impact:** High. Someone who quits Snapmark (or whose Mac restarts for an update) with an editor open behind other windows loses that screenshot and its marks without a word.
- **Current experience:** The menu's "Quit" item uses the standard quit role. There is no check for open editors, so all of them close and their screenshots are deleted. Because editors have no Dock icon (see 2-13), it is easy to forget one is still open.
- **Visual:** Menu as read in the code: `… Snapmark 0.2.0 · Check for updates… · Quit`. Proposal: "2 screenshots are not in a session yet. [Review] [Quit anyway]".
- **Recommendation:** On quit, if any editor has changes, bring them forward and ask.
- **Tradeoff:** Quit is no longer instant when work is open.
- **Decision needed:** Should Quit stop and show unsaved editors, or save them automatically into the session?
- **Verified:** read in the code.

### 2-04 · A discarded screenshot cannot be recovered

- **Impact:** High. A mis-pressed ⌘W or Discard cannot be undone, because the captured image is deleted from disk the moment the window closes.
- **Current experience:** After ⌘W the temp screenshot file was gone from the test folder. There is no "reopen last capture" in the menu, so the only way back is to capture the screen again, which is impossible if the build has since changed.
- **Visual:** Harness: temp folder after ⌘W contains only `audit/` (the captured `mock-*.png` was deleted).

- **Tradeoff:** Screenshots linger in a temp folder; needs a clean-up rule.
- **Decision needed:** Do you want a "Reopen last screenshot" item, and for how long should discarded captures be kept?

### 2-05 · When saving fails, nothing is shown and the Add button goes dead

- **Impact:** Critical. If the session cannot be written (folder moved, iCloud not synced, disk full, no permission), the user gets no message, cannot retry with the button, and the only way out is Discard, which loses the work.
- **Current experience:** I made the session's image folder read-only and clicked "Add to session ⌘↵". The window stayed open, the button became disabled but looks exactly as before, and no message appeared anywhere. The error only went to the developer console: "EACCES: permission denied".
- **Visual:** `shots/2-save-failed-ann.png` — box on "Add to session ⌘↵": "Save failed here: no message, button now dead".
  Proposal (not the real app), at the foot of the side panel:
  ```
  ┌──────────────────────────────────────────────┐
  │ ⚠ Could not add to "2026-09-25 09.14":       │
  │   the folder is read-only.                   │
  │   [Try again]  [Choose another session…]     │
  └──────────────────────────────────────────────┘
  ```
- **Recommendation:** Catch the failure, show a plain message next to the button naming the session and the reason, re-enable the button, and offer another session. The marks stay on screen.
- **Tradeoff:** A little more UI in the side panel for a rare case.
- **Decision needed:** Routine fix: no individual decision needed.

- **Owner's words:** "Also I wonder what the best way of making this portable is: being able to share this as a PDF or zip it, maybe both. Having it in the cloud." — 2026-09-25 (sessions in cloud folders are where writes fail).

### 2-09 · An open editor keeps saving into the session it started in, even after a switch or a new session

- **Impact:** Medium. In scene 1, a user who presses ⌘⇧2 ("New session") or picks another session while an editor is open expects the screenshot to go to the new session; it goes to the old one.

The notification "New session: 2026-09-25 15.20" appears, yet the open editor still shows "→ 2026-09-25 09.14" and saves there. - **Decision needed:** When you switch or start a session while an editor is open, should that editor follow, or stay with the session it was captured for?
