# Evaluator 5 · Accessibility (WCAG 2.2 A and AA)

Build: main at v0.2.0 (the compiled `dist/`). Editor seen through the audit harness, on the mock
"Acme Ops" page, at 1180 × 600, light and dark, 1× and 2×. Real key presses were sent with
Electron's `sendInputEvent`, and the accessibility tree was read from Chromium's DevTools protocol,
using a copy of the harness (`shots/5-harness.js`) that adds only those two things. The menu bar
menu, capture overlay, notifications, native dialogs and PDF were read in the code.

All screenshots named below are in the audit's `shots/` folder. Annotated ones start `5-a-`,
proposal sketches `5-p-`.

---

## Findings

### 5-01 · A keyboard-only user cannot put a single mark on the screenshot

- **Impact:** High: someone who cannot use a mouse or trackpad cannot do the product's core job at all: no marker, box, cross, tick, card, highlight, redaction or cut.
- **Current experience:** Tab moves through the 8 tool buttons, "Color", "Undo", "Comment", "Discard" and "Add to session", then wraps. The screenshot is never focused. Choosing "5 Numbered" by key works, but the hint then says "Press 5 and click the image to add a numbered marker with a note": there is no way to place it without a click. Every tool starts on a mouse-down on the image.
- **Visual:** `5-a-canvas-unnamed.png` (the area Tab never reaches). Proposal: `5-p-keyboard-marks.png`: the screenshot takes focus, arrow keys move a crosshair, Shift+arrows size it, Enter places the current tool's mark.
- **Recommendation:** Make the screenshot focusable (it sits in the Tab order after the toolbar). When it has focus, show a crosshair in the centre: arrows move it (Shift for bigger steps), Enter places a click-size mark of the current tool, and Enter, arrows, Enter draws a sized box, arrow or card from start to end. This also gives speed to mouse users who want to stay on the keys.
- **Tradeoff:** Placing things with the keys is slower than a mouse for most people, and it is new code in the editor's input handling. The freehand Pen can stay mouse-only, because WCAG exempts input that depends on the path.
- **Decision needed:** Should every tool except Pen be usable without a mouse, even if that adds a keyboard crosshair mode to the editor?
- **Verified:** seen on screen (the Tab order from real key presses) and read in the code.
- **Owner's words:** "This is also important: when I create, as I said, it needs to be shortcuts so I can just do this on the fly." — 2026-09-25

<details><summary>Supporting notes</summary>

- Where: editor window, the canvas, all tools of groups 1–7
- Broken: WCAG 2.1.1 Keyboard (A); checklist Accessibility 4
- Code: `src/editor.ts:432-490` (all placement is in `mouse:down`/`mouse:up`); `src/editor.html:187` (canvas, no tabindex)
- Screenshots: `5-tab-end.png`, `5-a-canvas-unnamed.png`, `5-p-keyboard-marks.png`; key log: Tab ×14 visits 13 controls and never the canvas
- Other products: Figma lets you move a selected object with the arrow keys; macOS Screenshot markup has no keyboard placement either
- Seen by: agent 5, keyboard-only walk-through

</details>

### 5-02 · Marks already on the screenshot cannot be selected, moved, resized or deleted from the keyboard

- **Impact:** High: a keyboard-only user who gets a mark in the wrong place (or a mouse user who wants precise nudging) has no way to fix it except undoing everything after it.
- **Current experience:** "V Select" can be chosen with the V key, but selecting a mark needs a click on it. Once selected, Backspace deletes it, but arrow keys do nothing, and there is no key to go from one mark to the next.
- **Visual:** `5-a-handles.png` (a selected cross; only the mouse can get it there). Proposal: `5-p-keyboard-marks.png`, right-hand "Marks" list.
- **Recommendation:** With Select active and the screenshot focused, Tab and Shift+Tab step through the marks, arrow keys move the selected mark by one pixel (Shift: 10), and Alt or Option with arrows resize it. Alternatively, or as well, list the marks in the side panel, where each row selects its mark.
- **Tradeoff:** Tab inside the screenshot changes what Tab means there; the list is more code but also answers 5-03.
- **Decision needed:** Keyboard selection inside the screenshot, a list of marks in the side panel, or both?
- **Verified:** read in the code; Backspace on a selection seen on screen.
- **Owner's words:** "Help me think about how we can highlight stuff and potentially add UI elements, like being able to add a card and write on the card, so I can actually edit on the screen and drag and drop, size, and so on." — 2026-09-25

### 5-03 · Card text cannot be edited again from the keyboard

- **Impact:** Medium: once you leave a card, fixing a typo on it needs a double-click.
- **Current experience:** A new card opens for typing straight away. After Escape or a click elsewhere, going back into the text is Fabric's double-click. No key opens a selected card for editing.
- **Visual:** Before: select a card (mouse only, see 5-02), press Enter: nothing happens. After (proposal): Enter on a selected card opens it for typing; Escape leaves.
- **Recommendation:** Enter on a selected card starts editing. This is also the macOS convention for renaming a selected item in Finder.
- **Tradeoff:** None worth naming; it depends on 5-02 for getting the card selected.
- **Decision needed:** Routine fix: no individual decision needed (once 5-02 is decided).
- **Verified:** read in the code.
- **Owner's words:** "being able to add a card and write on the card, so I can actually edit on the screen" — 2026-09-25

### 5-04 · Capturing needs a mouse: there is no keyboard way to take a screenshot

- **Impact:** High: a keyboard-only user can press ⌘⇧1 but cannot finish the capture, so the whole flow is closed to them before the editor opens.
- **Current experience:** "Capture region" runs macOS's interactive capture, which needs a drag for a region, or Space and a click for a window. The menu offers nothing else: no whole-screen and no front-window capture.
- **Visual:** Before: menu "Capture region ⌘⇧1" only. After (proposal): also "Capture screen" and "Capture front window", each with a shortcut.
- **Recommendation:** Add "Capture screen" (the display under the pointer) and "Capture front window" menu items. Both are one command with no pointer. The editor's Cut & move or a later crop covers the rest.
- **Tradeoff:** Two more menu items and shortcuts to find a free key for; whole-screen captures are larger images (they are already scaled down for the AI).
- **Decision needed:** Should Snapmark offer a capture that needs no pointer (whole screen or front window), and with what shortcut?
- **Verified:** read in the code.
- **Owner's words:** "This is also important: when I create, as I said, it needs to be shortcuts so I can just do this on the fly." — 2026-09-25

### 5-05 · Choosing a tool with the keyboard throws focus back to the start of the page

- **Impact:** Medium: a keyboard or VoiceOver user who presses Space on a tool button loses their place; the next Tab starts again at "1 Box".
- **Current experience:** Tab to "2 Arrow", press Space: the tool changes to Arrow, and focus lands on nothing (the page body). The next Tab goes to "1 Box". The same happens when a toolbar button has focus and you press a number key. VoiceOver says nothing about the change.
- **Visual:** `5-a-focus-loss.png`. Key log: Tab → "2 Arrow"; Space → focus on the page body, tool = Arrow; Tab → "1 Box".
- **Recommendation:** Update the existing buttons in place (their label, dots and pressed state) instead of rebuilding the toolbar on every change, so focus stays on the button that was pressed.
- **Tradeoff:** None for users.
- **Decision needed:** Routine fix: no individual decision needed.
- **Verified:** seen on screen (real key presses, focus logged after each).
- **Owner's words:** "When I press the same button multiple times, let's say I have the 1 button, I would switch between the shapes and it would indicate it at the top." — 2026-09-25

### 5-06 · The screenshot and every mark on it are invisible to screen readers

- **Impact:** High: a VoiceOver user hears an unnamed "canvas" and can't know what was captured or what has been drawn. Only numbered markers show up in the side panel.
- **Current experience:** The accessibility tree has two nodes of the role Canvas with no name. After drawing two crosses, a tick, a thumbs up, a highlight, two markers and a card, the only trace in the tree is "Note for 1", "Note for 2" and the card's unnamed hidden text field.
- **Visual:** `5-a-canvas-unnamed.png`. Proposal: `5-p-keyboard-marks.png`: the screenshot is named ("Screenshot, 8 marks") and a "Marks" list names each one ("Cross (remove)", "Tick (approve)", "Card: …").
- **Recommendation:** Give the screenshot a name that includes the mark count, and add a text list of marks to the side panel, each with its kind and, where there is one, its note or card text. The same list feeds 5-02 and 5-08.

- **Decision needed:** Should the side panel list every mark (not only numbered markers)?

### 5-07 · Every image in session.md and the PDF has the alt text "Screenshot 1", "Screenshot 2" …

- **Impact:** Medium: a teammate who reads the PDF or Markdown with a screen reader, and an agent that reads the text before the image, learn nothing from the alt text.
- **Current experience:** Each entry is `![Screenshot 1](img/001.png)`. The comment the user typed is right below the image, but not in the alt text.
- **Visual:** Before: `![Screenshot 1](img/001.png)`. After: `![Screenshot 1: Orders page. Remove: "Dashboard" link. Keep: "Paid" badge. 1 marker, 1 card.](img/001.png)`. See `5-p-session-text.png`.

- **Tradeoff:** Longer image lines in session.md cost a few tokens per entry.
- **Decision needed:** Should the alt text carry the comment and a summary of the marks, or only the comment?
- **Verified:** seen on screen (session.md printed by the harness after saving).

### 5-08 · Remove and approve marks exist only as pixels; session.md never says what goes and what stays

### 5-17 · Red means "remove" but is also the default colour for every neutral mark

## Accessibility rules the interaction guidelines must include

1. Every tool that draws or edits a mark works without a pointer. Pen is the only exception.
2. Every drag has a click-based or keyboard alternative (move, resize, arrow, redact, cut).
3. Focus never falls to the page body after an action; it stays on the control or moves to what the action created.
4. Keys act where they are used: tool keys and Delete only when the screenshot or toolbar has focus.
5. Every mark has a text form: in the editor's side panel, in the image's alt text and in session.md. The image never carries meaning the text lacks.
6. Remove and approve always differ by shape as well as colour; red and green are reserved for them.
7. Every line mark has a halo so it reads on any background; mark text picks black or white from its fill.
8. Text meets 4.5:1 and control edges 3:1 in both light and dark, including pressed states and placeholders.
9. Every control has a name that says what it does, and states (pressed, disabled, which of n) are exposed, not only drawn.
10. Every result is confirmed in words (tool change, save, copy, export) in a way VoiceOver reads.
11. Targets are at least 24 × 24 screen pixels, canvas handles included.
12. Exports are accessible documents: language, title, tags, headings with words in them, and real alt text.
13. The editor stays usable at 200% zoom at its minimum window size.

## Did not run

- **VoiceOver itself.** Names and roles come from Chromium's accessibility tree, not from listening to VoiceOver; what VoiceOver actually says (for example for "⌘↵" and "●○") is inferred.
- **The menu bar menu, capture overlay, notifications and the sessions folder dialog.** Not scriptable; read in the code only. The tray icon's accessible name (Electron's tooltip "Snapmark") was not checked with VoiceOver.
- **The PDF file.** Not opened or checked for tags; the finding comes from the print options in the code.
- **Real ⌘+ zoom.** Zoom was set on the window from the harness; whether a user can reach zoom with the keys (no app menu is set, Dock icon hidden) was not tested.
- **Colour-blindness simulation.** Not rendered; the red/green judgment uses the 1.43:1 luminance ratio and the shape cues.
- **Increase contrast, Reduce transparency and forced colours on macOS.** Not toggled; the editor has no `prefers-contrast` handling in its CSS.
- **1440 and 1920 wide, and 2× for every shot.** Contrast does not depend on size; target sizes were measured at 1180 × 600 and 1× only (the handle size at other widths scales with the display factor).
- **First run and the DMG.** Not in this agent's checks beyond the capture path.
